# LLM-Wiki & Filesystem Sync — Feature Spec

**Status:** Draft (revised)
**Date:** 2026-07-17
**Requires:** Phase 7 (Notes system, AI runtime), Phase 5 (MemoryEngine)

---

## 1. Overview

Extend the existing Notes system with LLM-powered features (auto-tagging, auto-categorization, auto-summarization, semantic search, RAG Q&A, chat-to-note conversion), a hierarchical category system that maps to filesystem folders, and one-way app-to-filesystem backup with import-for-restore.

---

## 2. Category System

### 2.1 Hierarchical Category Path

**CAT-01 — Path-based category:** Each note has an optional `categoryPath` field, e.g. `InfoTech/Database/MySQL`. The path uses `/` as a separator. No leading/trailing slashes. Each segment is a valid folder name. Path segments are normalized: no empty segments, no `.` or `..`, trim whitespace.

**CAT-02 — Category browse mode:** NoteList supports grouping by category. A tree view mode shows nested folders matching the category paths. Notes without a category appear under "Uncategorized". Clicking a category node shows a flat list of notes within that category.

**CAT-03 — Auto-categorize on save (LLM):** When auto-tagging runs (LLM-WIKI-01), the same LLM call also suggests a category path. The LLM receives the current category hierarchy (all existing distinct category paths) and the note content, and suggests a suitable path. User can accept, edit, or dismiss.

**CAT-04 — Category as filesystem folder (SYNC):** During filesystem backup, a note at path `InfoTech/Database/MySQL` is saved as `InfoTech/Database/MySQL/Note Title.md`. Nested folders are created automatically by the File System Access API.

**CAT-05 — Category normalization:** On save, the category path is normalized: leading/trailing slashes removed, duplicate slashes collapsed, whitespace trimmed from each segment. Invalid segments are flagged in-editor (antd red border on the category input).

## 3. LLM-Powered Features

### 3.1 Auto-Tagging & Auto-Categorization

**LLM-WIKI-01 — Tag + category on save:** When a note is saved, a Haiku-tier LLM call (temperature 0) analyzes the title + content and returns:
- Up to 5 suggested tags (keyword array)
- 1 suggested `categoryPath` (if applicable, else null)
- 1-2 sentence summary

These are displayed in the editor as AntD Tag components with Accept/Reject per tag, and the category path in an inline input pre-filled with the suggestion. Accepted values merge with existing fields.

**LLM-WIKI-02 — Toggle in Options:** Each LLM feature has an independent toggle in Options → Notes section (auto-tag, auto-categorize, auto-summary). When off, no LLM call is made on save.

### 3.2 Auto-Summarization

**LLM-WIKI-03 — Summary field:** A `summary` string field on each note (optional). Generated by the combined LLM call in LLM-WIKI-01. Displayed as secondary text in NoteList items.

**LLM-WIKI-04 — Regenerate:** "Regenerate tags/summary" button in the editor toolbar. Re-runs the combined LLM call in-place.

### 3.3 Semantic Search (LLM-Routed Reranking)

**LLM-WIKI-05 — Natural language search:** The NoteList search bar accepts natural language queries. Flow:
1. MiniSearch fuzzy search (existing) — returns keyword-matching results
2. If results < 3 or user clicks "AI Search", a Haiku-tier LLM call reranks the top-10 MiniSearch results by semantic relevance to the query
3. Ranked results display with "AI-enhanced" indicator

No embedding model. No vector store. The LLM acts as a relevance judge using the existing `generateText` call pattern.

### 3.4 Ask Your Notes (RAG Q&A)

**LLM-WIKI-06 — RAG Q&A:** A "Ask notes" input at the top of the Notes page. User types a question:
1. MiniSearch retrieves top-5 relevant note snippets
2. Flash-tier LLM call synthesizes an answer with per-statement source citations (note title + wikilink)
3. Answer rendered as a `@ant-design/x` Bubble component inline, ephemeral (not saved as a note)
4. Citations rendered as clickable AntD Tag components that navigate to the source note

### 3.5 Chat-to-Note Conversion

**LLM-WIKI-07 — Save message as note:** A "Save to note" action on any assistant message (three-dot menu). Triggers an LLM call that:
1. Extracts key knowledge from that message + surrounding context
2. Generates a title, content in markdown, suggested tags, and suggested wikilinks to existing notes
3. Opens the NoteEditor pre-filled for user review/edit before save

User is always the gatekeeper — the LLM drafts, the user publishes.

### 3.6 Notes Maintenance

**LLM-WIKI-08 — Staleness detection:** A `summaryGeneratedAt` and `tagsGeneratedAt` timestamp on each note. When `note.updated > summaryGeneratedAt` or `note.updated > tagsGeneratedAt`, the editor shows a subtle hint: "Content has changed — [Regenerate tags/summary]".

**LLM-WIKI-09 — Orphan detection:** Algorithmic (no LLM). Notes with zero wikilinks AND zero backlinks show an "Orphan" badge in NoteList. A "Find context" button triggers RAG Q&A (LLM-WIKI-06) to surface related notes.

**LLM-WIKI-10 — Bulk maintenance:** A "Re-analyze all notes" button in Options → Notes section. Runs tag + category + summary regeneration for all notes sequentially. User-initiated only (never automatic — cost and surprise).

## 4. One-Way Filesystem Sync (App → Filesystem)

### 4.1 Folder Setup

**SYNC-01 — Folder picker:** A "Set backup folder" button in Notes options or NoteList toolbar. Uses `showDirectoryPicker()` to let the user select a folder. The `FileSystemDirectoryHandle` is persisted in a new IndexedDB store (`notes_backup_config` — cannot use `chrome.storage.local`, handles are non-JSON-serializable).

**SYNC-02 — Permission verification:** On NotesPage mount, verify the stored handle still has read/write permission via `handle.queryPermission()`. If denied or missing, sync is disabled and a banner is shown: "Backup folder not accessible. [Re-select folder] [Dismiss]".

### 4.2 Sync Behavior

**SYNC-03 — Per-save sync:** Every time a note is created, updated, or deleted in IndexedDB, the sync service immediately writes/updates/deletes the corresponding `.md` file. Fire-and-forget (no user-facing loading state). A 50ms debounce prevents rapid-save burst issues.

**SYNC-04 — File format:** Each note is saved at `{categoryPath}/{title}.md` with YAML frontmatter:

```markdown
---
id: "uuid-string"
created: 1712345678000
updated: 1712345679000
tags: [tag1, tag2]
categoryPath: "InfoTech/Database/MySQL"
summary: "Optional LLM-generated summary"
---
Note content as markdown...
```

- If `categoryPath` is empty/null, the file goes in the root backup folder
- Nested folders are created automatically
- File names use the note title, sanitized for filesystem compatibility: replace `/ \ : * ? " < > |` with `_`

**SYNC-05 — Title collision:** If two notes have the same title AND same category path, the second file appends a numerical suffix: `My Note.md`, `My Note (1).md`, `My Note (2).md`. Scan existing files for highest suffix before writing.

**SYNC-06 — External change detection:** On save, if the file's `lastModified` timestamp is newer than the last sync timestamp (filesystem vs in-memory), show a confirm dialog: *"This file was modified externally. Overwrite with app version? [Overwrite] [Skip]"*. Default action is Skip. A 2-second tolerance window prevents false positives from cloud-sync agents (iCloud, Drive, etc.).

### 4.3 Sync State

**SYNC-07 — Disabled when no folder:** If no backup folder is set, all sync operations are no-ops. No errors, no UI noise. A small indicator in the Notes toolbar: "Backup: off [Configure]".

**SYNC-08 — Status indicator:** AntD Tag in the Notes toolbar:
- "Backup: On" (green) — folder set and writable
- "Backup: Off" (gray) — no folder selected
- "Backup: Error" (red) — permission revoked or write failed. Tooltip shows last error.

### 4.4 Import for Restore

**SYNC-09 — Import from folder:** A "Restore from backup" button in Notes options → Import/Export section. Uses `showDirectoryPicker()` to select a folder. Walks the directory tree, parses `.md` files with YAML frontmatter, and upserts each note into IndexedDB:
- If note `id` exists in DB → update (overwrite content, preserve `updated` if newer)
- If note `id` doesn't exist → create new
- Import is additive (notes not in backup folder are NOT deleted)
- `categoryPath` is reconstructed from the file's folder path

**SYNC-10 — Import preview:** Before importing, show a summary modal: "Found 24 notes (12 new, 3 updated, 9 unchanged). Proceed? [Import] [Cancel]"

**SYNC-11 — Delete on sync:** When a note is deleted in the app, the corresponding `.md` file is deleted from the backup folder. If the nested category folder becomes empty after deletion, it is removed as well (clean backup).

## 5. Memory ↔ Notes Integration

**MEM-01 — Memory-aware RAG:** When answering "Ask notes" queries (LLM-WIKI-06), the retrieval step also queries `MemoryEngine` for relevant user facts/preferences. If a memory fact is highly relevant to the query, it is included as context alongside note snippets, giving the LLM personal context.

**MEM-02 — Note → Memory extraction:** When a note is saved, the LLM call that generates tags/summary also extracts memory-worthy facts from the note content (same schema as `MemoryExtractor`). These facts are routed through the existing `MemoryEngine` for conflict resolution and storage. This bridges the gap: notes become a fact source for future chat context injection.

**MEM-03 — Save from chat:** LLM-WIKI-07 (Save to note) uses both the conversation messages AND relevant memory facts (via `MemoryEngine.assemble()`) to produce a richer note that incorporates the user's known preferences and patterns.

### 6.4 Data Flow Diagram

**Main save pipeline:**
```
User saves note
  → NotesPage.handleSave()
    → NotesDB.updateNote()
    → [if enabled] NoteTagger.analyze(title, content, allCategories)
        → LLM call (Haiku-tier): tags + category + summary + memoryFacts
        → Show suggestions inline in NoteEditor (tags, category input, summary)
        → User accepts → merge into note
    → [if enabled] MemoryEngine (MEM-02: upsert facts from note)
    → NoteFileSync.sync(note, action: 'update')
        → Resolve path: categoryPath / title.md
        → Create nested dirs if needed
        → Write .md with YAML frontmatter + content
    → NoteMaintenance.updateTimestamps(noteId)
```

**RAG Q&A:**
```
User asks "How to deploy billing service?" (NotesPage "Ask notes" input)
  → NoteQA.ask(query, allNotes)
    → MiniSearch.search(query) → top-5 snippets
    → MemoryEngine.assemble() → relevant memory facts (MEM-01)
    → LLM (Flash-tier):
        "Answer based on these notes and user context. Cite sources."
    → return { answer, citations: [{noteId, title, snippet}] }
  → Render Bubble + citation Tags inline below input bar
```

**Chat-to-note:**
```
User clicks "Save to note" on a message (ChatMessage menu)
  → SaveToNoteDialog opens
  → NoteChatConverter.convert(messages, memoryContext)
      → LLM (Haiku-tier): draft title, content, tags, wikilinks, categoryPath
  → Dialog shows pre-filled NoteEditor with LLM draft
  → User edits → saves → NotesDB.createNote() → NoteFileSync.sync()
```

**Restore:**
```
User clicks "Restore from folder" (ImportExportSection or NotesSection)
  → showDirectoryPicker()
  → Walk tree, parse all .md files (YAML frontmatter)
  → Show preview modal: "N notes found (X new, Y updated, Z unchanged)"
  → User confirms → upsert into IndexedDB
```

## 8. Decisions

| Decision | Rationale |
|----------|-----------|
| **D-01 — Single LLM call for tags + category + summary** | One Haiku-tier call covering all three is cheaper and faster than three separate calls. The prompt returns structured JSON with all three outputs. |
| **D-02 — Notes are dual-friendly: human body, machine frontmatter** | Note body is natural language markdown (user reads this). YAML frontmatter is structured metadata (LLM reads this: id, tags, categoryPath, summary). Both consumers get what they need from one file. Neither is compromised for the other's sake. |
| **D-03 — Category is path-based, not flat** | `categoryPath` maps 1:1 to filesystem folders. Flat tags already exist for many-to-many associations. This avoids duplicating the tag concept. |
| **D-04 — LLM wikilink suggestions dropped from v0.1** | MiniSearch already covers title-based wikilink matching. The edge case (semantically related notes with zero keyword overlap) is rare and doesn't justify the implementation complexity. |
| **D-05 — Notes feed into MemoryEngine, not the reverse** | Notes are user-curated knowledge. Extracting memory facts from notes enriches chat context without polluting notes with auto-extracted noise. Memory is system-owned; notes are user-owned. |
| **D-06 — Maintenance is user-initiated** | No background jobs in MV3 extensions. Staleness detection uses passive timestamp comparison. Bulk regeneration is explicitly triggered by the user. |
| **D-07 — Haiku-tier for analysis, Flash-tier for synthesis** | Tag/category/summary extraction is low-complexity (Haiku). RAG Q&A answer synthesis benefits from higher-quality output (Flash). |
| **D-08 — Backup folder handle in IndexedDB** | `FileSystemDirectoryHandle` is non-JSON-serializable and cannot go in `chrome.storage.local`. A dedicated IndexedDB store handles this. |

---

## 9. Out of Scope

| Feature | Reason |
|---------|--------|
| Bidirectional filesystem sync | Requires polling or Native Messaging. Complex, not needed for backup use case. |
| Embedding-based vector search | Large model download unsuitable for Chrome extension. LLM-routed reranking is sufficient. |
| LLM wikilink suggestions in autocomplete | Minimal utility beyond existing MiniSearch. Deferred to v0.2+. |
| Real-time collaborative editing | Requires backend infrastructure — out of scope. |
| Filesystem as primary note store | IndexedDB is primary. Filesystem is backup. |
| Image/file attachments in notes | No current requirement. |
| Auto-create notes from chat (unprompted) | User must explicitly trigger "Save to note". No background note generation. |

## 10. UX Flow Summary

**Daily writing flow:**
1. User writes a note and saves
2. Tags + category + summary auto-suggested → user reviews and accepts
3. Note indexed for search, memory facts extracted
4. `.md` file silently written to `BackupFolder/{categoryPath}/{title}.md`

**Research flow:**
1. User types "how do I deploy to staging?" in "Ask notes"
2. MiniSearch finds 5 relevant notes, MemoryEngine finds 2 user facts
3. LLM synthesizes answer with citations
4. User clicks a citation → navigates to that note

**Chat-to-note flow:**
1. Assistant provides deployment instructions in chat
2. User clicks "..." → "Save to note"
3. LLM drafts a note: title, tags, wikilinks to existing notes
4. Full conversation context + memory facts inform the draft
5. NoteEditor opens pre-filled → user reviews → saves

**Restore flow:**
1. New device or cleared IndexedDB
2. Options → Import/Export → "Restore from folder"
3. Select backup folder → preview: "24 notes found (category structure preserved)"
4. Import → all notes + categories restored

**Backup flow (normal):**
1. User sets backup folder once
2. Every save auto-writes the file
3. Status indicator shows "Backup: On" in green
4. If permission lost → indicator turns red → user re-selects folder
