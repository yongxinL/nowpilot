# Phase 5: Persistent Memory Architecture - Research

**Researched:** 2026-07-13
**Domain:** In-memory full-text search (MiniSearch), memory orchestration, weighted scoring, IndexedDB schema migration, BroadcastBus single-writer routing
**Confidence:** HIGH

## Summary

Phase 5 builds a system-owned `MemoryEngine` that orchestrates three memory layers (ConversationMemoryStore, UserMemoryStore, PreferenceMemoryStore) on top of the existing `MemoryDB` IndexedDB store. The engine integrates into the AgentOrchestrator pipeline at two points: pre-optimization (`assemble()`) which populates `ContextOptimizerInput.memory` and `.preferences`, and post-execution (`extract()`) which runs async fire-and-forget after the renderer completes.

The existing codebase provides a solid foundation: `MemoryDB` already has `memory_messages`, `memory_userFacts`, and `memory_summaries` object stores with working CRUD methods. `ContextOptimizerInput` already defines `memory?: Array<{id, content, score}>` and `preferences?: Record<string, unknown>`. `AgentOrchestrator.runWithContext()` is the integration point — the memory layer plugs in before `contextOptimizer.optimize()` and after `executeRenderer()` completes.

**Primary recommendation:** Build MemoryEngine as class+singleton with constructor DI following the exact same pattern as `ContextOptimizer` (inject TokenEstimator, Compressor, etc.). Add `minisearch` v7.2.0 as a new dependency. Extend the existing `MemoryDB` schema by bumping IndexedDB version from 1→2 to add `status` field on facts and `state` field on conversations. Route memory writes through BroadcastBus using `chrome.storage.session` for primary-surface election.

## Architectural Responsibility Map

| Capability | Primary Tier | Secondary Tier | Rationale |
|------------|-------------|----------------|-----------|
| Memory retrieval & scoring | API/Backend (Background SW) | — | MemoryEngine is a core service, not a UI concern. Retrieval runs server-side in the background service worker context. |
| Conversation summary storage | API/Backend (Background SW) | Database/Storage (IndexedDB) | Summaries are generated by MemoryExtractor (Haiku call) and stored via MemoryDB → IndexedDB. |
| User fact storage (versioned) | Database/Storage (IndexedDB) | — | Facts are IndexedDB-resident with active/superseded states. |
| Preference storage | Frontend Server (Zustand stores) | Database/Storage (chrome.storage.sync) | Preferences merge ThemeStore + WorkspaceStore + own prefs; sources are Zustand-persisted. |
| Cross-surface write routing | CDN/Static (chrome.storage.session) | API/Backend (BroadcastBus) | Primary-surface election via session storage; write requests routed through BroadcastBus. |
| Memory injection into context | API/Backend (ContextOptimizer) | — | MemoryEngine.assemble() populates ContextOptimizerInput; ContextOptimizer handles budgeting. |

### Pattern 2: MiniSearch Two-Pass Retrieval
**What:** MiniSearch narrows to top-20 candidates by relevance score, then 5-factor scoring ranks them to top-N (3 for tiny, 5 otherwise).
**When to use:** In `UserMemoryStore.search()` — the MiniSearch result provides `keywordScore` to the scoring formula.
**Example:**
```typescript
// Source: MiniSearch docs [CITED: https://lucaong.github.io/minisearch/classes/MiniSearch.MiniSearch.html]
const index = new MiniSearch({
  fields: ['content', 'tags', 'category'],
  storeFields: ['id', 'content', 'category', 'confidence', 'source', 'useCount', 'updatedAt'],
  searchOptions: {
    boost: { content: 2, tags: 1.5 },
    prefix: true,
    fuzzy: 0.2,
  },
});

// Phase 1: MiniSearch narrows to top-20
const candidates = index.search(query, { prefix: true, fuzzy: 0.2 })
  .slice(0, 20)
  .map(r => ({
    fact: r as unknown as UserMemoryFact,
    keywordScore: r.score / (index.search(query).length > 0 ? 
      index.search(query)[0].score : 1), // normalize to [0,1]
  }));

// Phase 2: 5-factor scoring
const ranked = memoryScorer.score(candidates, query);
```

### Pattern 3: IndexedDB Schema Migration (v1 → v2)
**What:** Bump `DB_VERSION` to 2, add `oldVersion < 2` upgrade branch to add new fields to existing stores. Use the transaction parameter for data migration if needed.
**When to use:** For adding `status` field to `memory_userFacts` (active/superseded) and `state` field to memory stores.
**Example:**
```typescript
// Source: idb docs [CITED: https://github.com/jakearchibald/idb/blob/main/_autodocs/configuration.md]
export const DB_VERSION = 2; // bumped from 1

// In getDB() upgrade callback:
upgrade(db, oldVersion, _newVersion, _transaction) {
  if (oldVersion < 1) {
    // ... existing v1 stores (unchanged)
    db.createObjectStore('memory_userFacts', { keyPath: 'id' });
    // ...
  }
  if (oldVersion < 2) {
    // Add status field to existing facts
    // Since IndexedDB is schemaless per-store, new fields on put() are auto-added
    // But we may want to migrate existing records:
    const tx = _transaction;
    const factStore = tx.objectStore('memory_userFacts');
    // Could iterate existing facts and add status: 'active' default
    // Or rely on runtime default at read time (simpler)
  }
}
```

**Key insight:** IndexedDB object stores are schemaless at the value level — adding a `status` field does NOT require altering the store definition, only bumping the version so the `upgrade` callback triggers. The planner should note this: the `NowPilotDB` TypeScript interface MUST be updated to include the new fields, but the upgrade callback can be minimal (just version bump + no-op, relying on runtime defaults).

### Pattern 4: BroadcastBus Single-Writer Routing
**What:** Non-primary surfaces emit memory write requests via `chrome.storage.session.set({ np_memory_write_request: payload })`. The primary surface listens via `chrome.storage.onChanged` and executes the write through WriteJournal + MemoryDB.
**When to use:** All memory mutation operations from non-primary surfaces.
**Example:**
```typescript
// Source: Existing BroadcastBus pattern (broadcastBus.ts lines 16-34)
// Write request message type:
interface MemoryWriteRequest {
  type: 'upsert-fact' | 'update-summary' | 'archive-conversation';
  payload: unknown;
  surfaceId: string;
  timestamp: number;
}

// Non-primary surface:
async function requestMemoryWrite(request: MemoryWriteRequest) {
  await chrome.storage.session.set({ np_memory_write_request: request });
}

// Primary surface listener (in Background SW):
chrome.storage.onChanged.addListener((changes, areaName) => {
  if (areaName === 'session' && changes.np_memory_write_request) {
    const request = changes.np_memory_write_request.newValue as MemoryWriteRequest;
    // Execute write through WriteJournal + MemoryDB
    executeMemoryWrite(request);
    // Clear the request queue key
    chrome.storage.session.remove('np_memory_write_request');
  }
});
```

### Anti-Patterns to Avoid
- **Direct MemoryDB writes from UI components:** MemoryEngine MUST be the sole orchestrator. UI code never calls `memoryDB.putUserFact()` directly. This is system-owned memory per D-01.
- **Embedding-based search:** Do not introduce embedding models or vector databases in v0.1. The PRODUCT_SPEC §3.2 explicitly constrains to MiniSearch bag-of-words.
- **Blocking extraction:** `MemoryEngine.extract()` MUST be fire-and-forget. Never `await` it in the render pipeline. It runs after the user-facing response is delivered.
- **Schema migration via data copy:** Do not copy all facts into a new store during migration. IndexedDB stores are schemaless; just bump the version, update the TypeScript interface, and rely on runtime defaults for missing fields.

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Full-text search | Custom TF-IDF or inverted index | `minisearch` v7.2.0 [VERIFIED: npm registry] | Battle-tested (1.3M wkly downloads), handles stemming/tokenization/ranking, supports prefix+fuzzy+boosting out of the box. |

| Conversation archiving | Custom LRU cache | `MemoryEngine` with WriteJournal ops | The 10-active / 100-archived caps are app-specific policy; WriteJournal provides the consistency guarantees. |
| Fact versioning | Homegrown versioned records | `conflictResolver` module | The active/superseded state machine with confidence thresholds is domain logic, not a general-purpose library problem. |
| Preference merging | Manual object spread | PreferenceMemoryStore merge logic | Preferences merge ThemeStore + WorkspaceStore + own prefs; this is app-specific domain logic. |

**Key insight:** The only new external dependency is `minisearch`. Everything else is either already installed or is domain logic that belongs in dedicated modules. Do NOT introduce additional libraries for LRU, scoring, or conflict resolution — those are in-house logic that the planner will design.

## Common Pitfalls

### Pitfall 1: MiniSearch Index Not Rebuilt After Fact Upserts
**What goes wrong:** New or superseded facts are not reflected in search results because the MiniSearch index is stale.
**Why it happens:** MiniSearch is an in-memory index. Unlike IndexedDB, it must be explicitly updated when documents change.
**How to avoid:** Every `UserMemoryStore.upsert()` call MUST call `index.replace(fact)` for updated facts, `index.add(fact)` for new facts, and `index.discard(factId)` for evicted facts. The MiniSearch index is rebuilt from IndexedDB on startup.
**Warning signs:** Search returns facts that were superseded, or doesn't return newly added facts.

### Pitfall 2: Extraction Blocking the Render Pipeline
**What goes wrong:** Memory extraction runs synchronously before the response is delivered, increasing time-to-first-token by 1-3 seconds.
**Why it happens:** Forgetting that `MemoryEngine.extract()` is fire-and-forget (D-04), and `await`-ing it in AgentOrchestrator.
**How to avoid:** In `AgentOrchestrator.runWithContext()`, call `memoryEngine.extract(...)` WITHOUT `await` (or use `.catch()` for error handling). The extraction MUST run after `yield*` completes for the renderer.
**Warning signs:** User sees delay between clicking send and seeing the response start streaming.

### Pitfall 3: IndexedDB Schema Version Mismatch
**What goes wrong:** `DB_VERSION` is bumped but the TypeScript `NowPilotDB` interface is not updated, causing type errors on `put()`/`get()` calls with new fields.
**Why it happens:** The `idb` library uses the TypeScript interface for type safety. Adding fields to the runtime schema doesn't update the compile-time types.
**How to avoid:** When adding `status`, `useCount`, `lastUsedAt` to `memory_userFacts` and `state`/`archivedAt` to `memory_summaries`, update BOTH the `NowPilotDB` interface AND the `DB_VERSION` constant. All store method signatures in `MemoryDB` must also be updated.
**Warning signs:** TypeScript errors on `memoryDB.putUserFact()` with new fields; tests fail because mock DB doesn't have new fields.

### Pitfall 4: Preference Store Creating Circular Dependencies
**What goes wrong:** `PreferenceMemoryStore` importing from `workspaceStore.ts` and `themeStore.ts`, which in turn depend on code that eventually imports `MemoryEngine`.
**Why it happens:** Zustand stores are typically imported for `getState()`. If `MemoryEngine` depends on something that depends on WorkspaceStore, and PreferenceMemoryStore imports WorkspaceStore, you get a cycle.
**How to avoid:** `PreferenceMemoryStore` should NOT use Zustand store hooks or react bindings. Use `useWorkspaceStore.getState()` (Zustand vanilla API) at call time, not at module import time. This is read-only and synchronous. Alternatively, inject the required store state via constructor or method parameters.
**Warning signs:** Circular import errors at build time; "Cannot access before initialization" errors.

### Pitfall 5: BroadcastBus Race on Session Storage
**What goes wrong:** Two surfaces both try to write to `np_memory_write_request` simultaneously, one overwrites the other before the primary processes it.
**Why it happens:** `chrome.storage.session.set()` is async; two surfaces may call it within the same event loop tick.
**How to avoid:** Use a write queue pattern: each surface appends to an array in session storage, or uses a unique key per write request (`np_memory_write_req_{uuid}`). The primary surface drains all matching keys. The existing `np_memory_write_queue` key naming from the spec suggests an array-based approach.
**Warning signs:** Memory writes from one surface silently disappear; facts failing to persist from Side Panel.

### MiniSearch Index Configuration for User Facts
```typescript
// Source: Context7 MiniSearch docs [CITED: https://github.com/lucaong/minisearch/blob/master/README.md]
// Verified pattern: configure fields, storeFields, searchOptions
import MiniSearch from 'minisearch';

export class MiniSearchIndex {
  private index: MiniSearch;

  constructor() {
    this.index = new MiniSearch({
      fields: ['content', 'tags', 'category'],
      storeFields: ['id', 'content', 'category', 'confidence', 'source', 'useCount', 'updatedAt'],
      searchOptions: {
        boost: { content: 2, tags: 1.5 },
        prefix: true,
        fuzzy: 0.2,
      },
      idField: 'id',
    });
  }

  search(query: string, limit = 20) {
    return this.index.search(query, {
      prefix: true,
      fuzzy: 0.2,
    }).slice(0, limit);
  }

  addFact(fact: { id: string; content: string; tags: string[]; category: string; [key: string]: unknown }) {
    this.index.add(fact as any);
  }

  replaceFact(fact: { id: string; content: string; tags: string[]; category: string; [key: string]: unknown }) {
    this.index.replace(fact as any);
  }

  removeFact(id: string) {
    this.index.discard(id);
  }

  rebuild(facts: Array<{ id: string; content: string; tags: string[]; category: string; [key: string]: unknown }>) {
    this.index.removeAll();
    this.index.addAll(facts as any);
  }
}
```

### 5-Factor Scoring Implementation
```typescript
// Source: PRODUCT_SPEC §3.4 formulas [CITED: .planning/PRODUCT_SPEC_v0_1.md lines 494-506]
export class MemoryScorer {
  score(
    candidate: { fact: UserMemoryFact; keywordScore: number },
    query: string,
    matchedTags: string[],
  ): number {
    const now = Date.now();
    const DAY = 86400000;

    // All sub-scores normalized to [0, 1]
    const keywordScore = candidate.keywordScore; // from MiniSearch, already ≈[0,1]
    const tagScore = matchedTags.length / Math.max(1, candidate.fact.tags.length);
    const recencyScore = Math.max(0, Math.min(1, 1 - (now - candidate.fact.updatedAt) / (30 * DAY)));
    const useCountScore = Math.min(1, (candidate.fact.useCount ?? 0) / 20);
    const confidenceScore = candidate.fact.confidence; // already [0, 1]

    return (
      keywordScore * 0.45 +
      tagScore * 0.25 +
      recencyScore * 0.15 +
      useCountScore * 0.10 +
      confidenceScore * 0.05
    );
  }

  tieBreak(results: ScoredFact[]): ScoredFact[] {
    return results.sort((a, b) => {
      // Deterministic: score → confidence → recency → useCount → id
      return (
        b.finalScore - a.finalScore ||
        b.fact.confidence - a.fact.confidence ||
        (b.fact.updatedAt - a.fact.updatedAt) ||
        ((b.fact.useCount ?? 0) - (a.fact.useCount ?? 0)) ||
        a.fact.id.localeCompare(b.fact.id)
      );
    });
  }
}
```

## Open Questions (RESOLVED)

1. **AgentOrchestrator.runWithContext() signature change** (RESOLVED — Pattern A chosen: caller-assembles)
   - What we know: `runWithContext(optimizedContext, preferredProviders)` currently takes 2 params. MemoryEngine needs `conversationId`, `userMessage`, and `tier` for `assemble()`, plus the full message list for `extract()`.
   - Resolved: Pattern A (caller-assembles) selected. The caller calls `memoryEngine.assemble()` before creating `ContextOptimizerInput`, then passes enriched OptimizedContext to `runWithContext()`. This requires no signature change to `runWithContext()` and matches the current architecture. See 05-07-PLAN.md Task 2 for implementation details.

2. **MiniSearch Index Persistence Across SW Restarts** (RESOLVED — rebuild on startup)
   - What we know: Service workers can be terminated at any time. MiniSearch index is in-memory.
   - Resolved: Rebuild from MemoryDB on startup (simpler, always consistent, fast with ≤500 facts). `MiniSearchIndex.rebuild()` is called at SW startup via `userMemoryStore.initialize()`. See 05-04-PLAN.md Task 2 for implementation details.

3. **Haiku-Tier Extraction Model Selection** (RESOLVED — lowest-cost tier via TierResolver)
   - What we know: MemoryExtractor uses Haiku-tier models via existing ProviderRouter + TierResolver.
   - Resolved: Use the lowest-cost tier available. If only one provider, use its cheapest model. TierResolver already handles this mapping. The extractor prompt is compact (<200 tokens output) to minimize cost. See 05-05-PLAN.md Task 1 for implementation details.

4. **BroadcastBus Write Request Deduplication** (RESOLVED — idempotency key in MemoryWriteRequest)
   - What we know: Non-primary surfaces emit write requests via `chrome.storage.session`. The primary surface processes them.
   - Resolved: Write requests carry an idempotency key (UUIDv4 in `MemoryWriteRequest.idempotencyKey`). MemoryEngine maintains a `#processedKeys` Set (capped at 1000 entries) that the primary surface checks before executing. If a new primary picks up a stalled request, the idempotency check prevents double-processing. This matches WriteJournal's existing idempotency pattern. See 05-06-PLAN.md Task 3 for implementation details.

### Known Threat Patterns for Memory + Chrome Extensions

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Malicious fact injection via extraction | Tampering | Zod schema validation on MemoryExtractor output; confidence score gating (D-16 requires 2+ observations to supersede). |
| Cross-surface write race | Tampering | Single-writer via BroadcastBus + chrome.storage.session election (D-06). WriteJournal idempotency for replay protection. |
| Memory exhaustion from unbounded facts | Denial of Service | Hard cap of 500 facts (D-23); low-confidence eviction after 30 days (D-24); LRU eviction for conversations (D-22). |
| Prompt injection via memory content | Spoofing | MemoryEngine.assemble() injects facts as structured JSON, not free-form text in the system prompt. ContextOptimizer budgets memory sections (10-15%). |
| Stale MiniSearch index after crash | Information Disclosure | Index rebuilt from MemoryDB on SW startup. Discarded facts are removed from search results immediately. |
| API key leak in extraction call | Information Disclosure | Uses existing ProviderRouter which reads keys from EncryptedStorage at call time — no new key handling. |
