**Types (export all):**
- `WriteJournalOperation` — union type: `'update-workspace' | 'append-memory-message' | 'evict-conversation' | 'archive-conversation' | 'compact-conversation' | 'save-note-with-links' | 'update-user-memory' | 'export-data'` (per RESEARCH.md lines 647-654)
- `WriteJournalStatus` — union type: `'pending' | 'applying' | 'completed' | 'failed' | 'rolled-back'`
- `WriteJournalStep` — `{ name: string; status: 'pending' | 'completed' | 'failed'; error?: string }`
- `WriteJournalEntry` — `{ id: string; operation: WriteJournalOperation; status: WriteJournalStatus; createdAt: number; updatedAt: number; attempts: number; targetIds: Record<string, string>; steps: WriteJournalStep[] }`

**Functions:**
- `createEntry(operation, targetIds, steps): Promise<WriteJournalEntry>` — generate UUID via `crypto.randomUUID()`, set status 'pending', createdAt/updatedAt = Date.now(), attempts = 0, persist in WriteJournalDB.entries store.
- `commitEntry(entryId): Promise<void>` — read entry, set status 'applying', increment attempts, update updatedAt, persist. Execute each `step` sequentially (call `step.executor()` — each step has an `executor: () => Promise<void>` field). On each success, mark step 'completed' and persist. After all steps, set status 'completed', persist. On failure, set status 'failed', capture error on failed step.

    Note: `steps` should be `Array<{ name: string; executor: () => Promise<void> }>` for the createEntry API, and the internal stored form uses `WriteJournalStep[]` (the executor is not serialized — only name+status+error). On replay, the executor is looked up by step name from a registry (`stepExecutors: Map<string, () => Promise<void>>`).

- `replayJournal(stepExecutors): Promise<number>` — called on startup. Opens WriteJournalDB, gets all entries, filters to non-terminal (not completed/failed/rolled-back). For each: set status 'applying', increment attempts, persist. Execute incomplete steps via `stepExecutors.get(step.name)()`. On success, set status 'completed'; on failure, set status 'failed' with error. Returns count of replayed entries. Per RESEARCH.md lines 340-371.

- `repairEntry(entryId, stepExecutors): Promise<void>` — lazy repair on record access. Validates a single entry, replays incomplete steps, marks completed or failed. Used as secondary safety net per D-06.

- `getEntriesByStatus(status): Promise<WriteJournalEntry[]>` — query helper using idb index on 'by-status'.

- `getEntry(id): Promise<WriteJournalEntry | undefined>` — single entry lookup.

**Database setup:**
Use idb's `openDB('WriteJournalDB', 1, { upgrade })` with a v1 schema:
- Object store 'entries' with keyPath 'id'
- Index 'by-status' on status field (create in same v1 upgrade)

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| IndexedDB WriteJournalDB → WriteJournal | Journal entries persisted in IndexedDB; replay must validate entry integrity before executing steps |
| WriteJournal → chrome.storage.local / BroadcastBus | Replayed steps may write to storage or emit messages; step executors must be idempotent |
| Extension page A → Extension page B (via BroadcastBus) | Workspace update notifications cross surface boundaries; message integrity is important |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-06 | Tampering | WriteJournal.entries | high | mitigate | Each entry has attempts counter; replay increments it; entry transitions through explicit status lifecycle (pending→applying→completed); no silent state transitions |
| T-02-07 | Denial of Service | WriteJournal.replayJournal | medium | mitigate | Replay has bounded iterations (attempts counter); entries that fail replay are marked 'failed' and skipped on subsequent replays; no infinite retry loop |
| T-02-08 | Information Disclosure | WriteJournal.entries (targetIds) | low | accept | targetIds may reference entity IDs (conversation IDs, note IDs); these are opaque UUIDs, not sensitive data; the journal itself contains no plaintext secrets |
| T-02-09 | Elevation of Privilege | MigrationRunner.migrate | medium | mitigate | idb's `upgrade()` runs in a version-locked transaction; `oldVersion < N` guards ensure steps never run out of order; idempotency checks prevent duplicate schema creation |
| T-02-10 | Denial of Service | MigrationRunner (blocked) | low | mitigate | `blocked` callback warns and closes; `blocking` callback closes old connection to unblock; worst case: user must close other tabs (typical IndexedDB behavior) |
| T-02-SC | Tampering | npm install (idb, fake-indexeddb) | high | mitigate | Already audited in 02-01 threat model T-02-SC; same packages covered |
</threat_model>
