<objective>
Ship the phase's architectural tracer: converge the scaffold's two parallel messaging paths (a raw `chrome.runtime.onMessage` listener in `background.ts` and a fully-built but never-initialized `MessageBus`) onto one typed-envelope path, end-to-end, from the content script through the background Service Worker and back. This is the single riskiest cross-cutting piece of Phase 1 — every later plan's UI wiring, workspace handoff, and command registration ultimately rides this messaging layer, so it is proven first, on its own, before any other Phase-1 work builds on top of it (D-13/D-14/REQ-R01).

Purpose: the scaffold's `entrypoints/background.ts:28-34` raw listener and `src/core/messaging/MessageBus.ts`'s `init()` (verified never called anywhere) are two disconnected implementations of the same job. Wiring them together now — as a thin vertical slice touching content script, background SW, and the typed envelope contract — surfaces any MV3 message-channel pitfall (double `sendResponse`, cold-start races, dropped messages) while the change surface is small, rather than after five more plans have layered UI on top of an unproven messaging path.

Output: `src/core/messaging/BackgroundRouter.ts` (new, thin typed wrapper); `entrypoints/background.ts` calling it as the sole message-registration entry point; the content script (renamed to `entrypoints/content/core.content.ts` per D-07a's path-shape normalization) sending `CONTENT_SCRIPT_READY`/`SPA_NAVIGATION` as typed `RuntimeEnvelope` values instead of raw object literals; two new real integration tests proving the cold-start and single-response contracts.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| content script (ISOLATED world, untrusted page context) -> background SW | Any page the user visits can trigger the content script's sendMessage calls; the background must not trust envelope contents beyond their declared shape |
| background SW <-> Side Panel / Standalone / Options surfaces | Cross-context messaging inside the extension's own trust boundary, but still worth validating sender identity |
