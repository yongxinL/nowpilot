<decisions>
## Implementation Decisions

### Split-Pane Layout (RICH-H-11, H-12)
- **D-01 — Three-column layout with collapsible right pane:** Keep the existing 240px standalone sider nav unchanged. Add a right-side Context Pane between the chat area and the right edge. The center column remains the Chat/Agent workspace. The right pane is a collapsible auxiliary workspace.
- **D-02 — Always visible by default, user collapses manually:** Right pane is visible by default on Chat/Agent pages. A persistent toggle button in the divider collapses/expands it. When collapsed, a narrow tab strip remains as a re-expand affordance. Collapse state persists across sessions via RightPaneStore. Never auto-show/hide based on content availability.
- **D-03 — Two preset widths, toggled:** Compact (~320px) and Expanded (~45–50% of available workspace). Toggle button in the divider switches between them. Width preference persisted in RightPaneStore. No freeform drag-resize.
- **D-04 — Auto-degrade to Drawer on small screens:** Below a responsive breakpoint (~900px right pane width), the pane transitions to a Drawer overlay. Compact mode becomes the default before the transition.
- **D-05 — Three tabs: Context (lightweight), Notes (search+preview), Tools (live status):** Context tab shows current + pinned page context as a quick-reference surface. Notes tab supports MiniSearch + inline note preview. Tools tab shows live MCP/server status with expandable capability details. Full editing/management remains in dedicated pages.
- **D-06 — User-selected tab, persisted, auto-switch only on explicit intent:** RightPaneStore remembers the last-selected tab across sessions. Pane auto-switches only on explicit user actions (opening a wikilinked note, clicking a pinned tab, viewing tool details). Background AI activity never changes the active tab.
- **D-07 — RightPaneStore (Zustand) for presentation state only:** A lightweight RightPaneStore manages pane UI state: activeTab, visibility, width, searchQuery, selectedNoteId, expandedToolId. Domain data reads from existing stores (workspaceStore, NotesDB/MiniSearch, MCP config). Content scripts never talk directly to the pane.
- **D-08 — Page availability:** Full right pane (3 tabs) on Chat and Agent pages. Context tab only on Notes page (for reference while writing). Hidden on Options, Diagnostics, and other configuration pages.

### Persona Onboarding & Identity (RICH-R-03, R-05)
- **D-09 — Replace onboarding Step 1 with "Meet NowPilot":** The existing Welcome step becomes the persona intro. Shows bunny avatar, identity (name, tagline, core values: privacy-first, helpful, precise, humble), and a lightweight non-interactive capability preview (3-4 cards: Summarize Pages, Research Topics, Draft Responses, Explain Code). After proceeding, existing provider setup flow continues unchanged from Step 2.
- **D-10 — Visible by default with subtle Skip link:** The Meet NowPilot step appears for all new users but includes a small Skip link for users who want to go directly to provider setup. Primary CTA remains Continue.
- **D-11 — Persona preferences in PreferenceMemoryStore, layered overrides:** Add persona-related fields (aiName, aiTone, responseBrevity) to preferenceSchema / PreferencePayload. PersonaService.getActiveProfile() applies preference overrides onto DEFAULT_PERSONA_PROFILE via deep merge. Only user-customized deltas are stored; the canonical profile remains in code.
- **D-12 — Rest of onboarding unchanged:** Steps 2–8 (Provider setup through Done) remain unchanged after the Meet NowPilot step.

### Template Browser (RICH-I-09, I-10)
- **D-13 — Sender toolbar popover only:** A Templates icon button in the Sender toolbar opens a categorized, searchable popover. Selecting a template inserts its prompt into the Sender. No tab in the right pane — templates stay close to where they're used.
- **D-14 — New user-facing displayCategory:** Templates grouped by capability-oriented categories: Writing, Analysis, Research, Coding, Support. The existing scope field remains for internal logic. A new displayCategory field on PromptTemplate controls presentation. All 21 built-in templates get assigned displayCategory values.
- **D-15 — TemplateBrowserService wrapping PromptManager:** A dedicated service handling category grouping, recent-usage tracking, search, and ranking. PromptManager remains responsible for registration/retrieval. The template browser UI consumes TemplateBrowserService, not PromptManager directly.
- **D-16 — Insert template with guided variable filling:** Clicking a template populates the Sender with the template content. Variables ({{topic}}, {{language}}) render as highlighted placeholders with tab-based navigation between fields. Templates without variables insert as plain text. User always reviews and optionally edits before sending.

### Inline Confirmation (RICH-C-12, C-13)
- **D-17 — Inline confirmation card in Bubble:** When a side-effect action is proposed in Chat mode, render a dedicated inline confirmation card with action description, rationale, and ActionChipGroup (Proceed/Cancel). Distinct from Agent mode's PermissionDialog modal — chat uses lighter-weight conversational confirmations.
- **D-18 — Extend PermissionService with tiered ConfirmationLevel:** Add ConfirmationLevel return type (AutoExecute, ConfirmInline, RequirePermission) to PermissionService. Read-only local operations auto-execute. External lookups (web search, URL fetch) trigger ConfirmInline. Side-effect actions (send, update, create) require RequirePermission. Single service for both Chat and Agent modes.
- **D-19 — No persistent memory for chat confirmations:** Chat-mode confirmations are one-time, per-action, non-persistent. No "remember this choice" or "always allow" option. Persistent permission grants remain exclusive to Agent mode via PermissionStore.
- **D-20 — Collapsed confirmation record after Proceed:** After clicking Proceed, the confirmation card collapses to a compact approved-action summary (e.g., "Searched the web") with a spinner. The tool result renders below when complete. Cancel removes the card and shows "Action cancelled." Provides audit trail without clutter.

### User Greeting & Identity (RICH-C-14, RICH-I-03)
- **D-21 — Optional displayName in PreferenceMemoryStore:** Add displayName field to preferenceSchema. If set, used in personalized greetings. If not set, fall back to generic greeting ("Good morning! How can I help?"). No Chrome Identity API permission required. No mandatory onboarding question for the name.
- **D-22 — Time-of-day greeting with contextual awareness:** Dynamic greeting: morning (<12pm) = "Good morning", afternoon (12-5pm) = "Good afternoon", evening (>5pm) = "Good evening". Optionally includes {displayName}. Persona tagline below. When relevant context exists, a single contextual line (e.g., "You're working on: [page title]" or "You have 4 pinned tabs").
- **D-23 — Greeting inside BrandedHeader, Welcome Cards below:** BrandedHeader renders the personalized greeting, persona tagline, and optional contextual line — the single surface for persona identity. WelcomeCards render independently below as a capability-discovery component. When Welcome Cards are dismissed, the greeting remains visible.
- **D-24 — GreetingService + useGreeting hook:** A lightweight GreetingService generates greeting text, persona subtext, and optional contextual line from user preferences + workspace context. ChatPage requests the computed greeting via a useGreeting hook and passes it into BrandedHeader.

### Conversation Closure (RICH-C-09)
- **D-25 — Conversation-end heuristic, shown once:** Display a lightweight feedback prompt ( "Did this help?" [👍] [👎]) only when the conversation appears complete: after 10-15s idle, no pending clarifications, no active follow-up interactions, and the latest assistant message appears to have resolved the user's request. At most once per conversation.
- **D-26 — useConversationClosure hook + ConversationClosure component:** A useConversationClosure hook computes completion state, manages idle timers, and determines when feedback should appear. A dedicated ConversationClosure component renders the 👍/👎 UI. ChatPage consumes the hook and passes state into the component.
- **D-27 — Feedback stored as conversation-level telemetry:** Feedback is logged as conversation metadata (not user memory). Anonymized, used for quality tracking.

### Brand Indicators (RICH-H-02, H-03)
- **D-28 — First-message branding only:** Show the NowPilot identity prominently on the first assistant message in each conversation (bunny avatar + branded header treatment). Subsequent messages render normally. Avoids repetitive branding on every Bubble.
- **D-29 — Agent mode ThoughtChain header:** Replace generic "Agent is processing..." with "NowPilot is working…" in the ThoughtChain header. A simple string replacement in the Agent UI component.

### Image Paste (RICH-H-16)
- **D-30 — onPaste on Sender wrapper:** Attach paste handler to the existing Sender container wrapper div. On paste, check clipboardData for image items. Convert blob to File, process through the existing attachment pipeline (resize, thumbnail generation, attachment preview). Normal text paste unchanged.
- **D-31 — Append all clipboard images:** If clipboard contains multiple images, attach all of them. Each renders as a separate thumbnail. Existing attachment-count limits apply; excess images handled by existing limit-enforcement rules.
- **D-32 — Thumbnail confirmation, focus stays in Sender:** Pasted images appear immediately in the attachment thumbnail strip. Cursor/focus remains in Sender so user can continue typing. No toast notification — the thumbnail is sufficient visual confirmation.
- **D-33 — Resize pipeline by default, configurable preference:** Pasted images go through the same optimization pipeline as drag-drop (max 800px dimension, JPEG quality 0.85). Add a "Preserve original image resolution" toggle in PreferenceMemoryStore for power users who need full resolution.

<specifics>
## Specific Ideas

- Right pane tabs use antd Tabs component with compact styling matching the existing sider nav aesthetic
- Template browser popover uses antd Popover with Input.Search + categorized accordion/sections
- Meet NowPilot step reuses the existing OnboardingModal step pattern (numbered circles, inline styles)
- Inline confirmation card reuses ActionChipGroup (variant="default") for Proceed/Cancel — same pattern as FollowUpAction divider + chips
- Image paste reuses the existing attachment thumbnail strip — pasted images are indistinguishable from drag-dropped images visually
- The collapsed confirmation record uses a compact antd Tag or Badge with check icon — consistent with ThoughtChain step indicators
- GreetingService is a pure function module (not a class) — takes preferences + context, returns greeting object
</specifics>
