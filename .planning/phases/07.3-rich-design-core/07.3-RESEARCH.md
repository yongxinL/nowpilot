**Researched:** 2026-07-18
**Domain:** AI UI Design (RICH paradigm), React component architecture, Ant Design X integration

## Summary

Phase 07.3 establishes the RICH design paradigm foundation for NowPilot. All 17 P0 must-have requirements are additive — new components, a persona subsystem, and enhanced rendering of existing chat surfaces. No new external packages are required; every addition uses the existing antd v6.5.0 and @ant-design/x v2.8.0 stack. The phase touches three architectural tiers: **core services** (PersonaInjector, FollowUpService, QuickActionService, WelcomeCardService), **React hooks** (useChat persona injection, stage tracking), and **UI components** (WelcomeCards, ActionChipGroup, ClarificationAction, FollowUpAction, BrandedHeader, StageIndicator, CodeBlockActions).

All foundation dependencies are already in place: PlannerService supports `ask_clarification` (pipelineTypes.ts line 4), PromptManager has 22 builtin templates with categories, UserMemoryStore supports preference tracking, workspaceStore provides `currentPageContext.hostname`, and the Think component from @ant-design/x renders stage indicators.

**Primary recommendation:** Build the persona subsystem first (RICH-R-01/R-02/R-11 — Wave 1), then the Welcome Cards + branded header (Wave 2), clarification + quick actions (Wave 3), and follow-up + code actions + stage indicators (Wave 4), as specified in the phase implementation plan. All integration follows existing patterns: Zustand stores, class+singleton core services, and Ant Design X Bubble/Sender/Think components.

**What:** Use @ant-design/x Bubble's `contentRender` and `footer` props to render custom UI (clarification chips, follow-up chips) inside AI messages without modifying the Bubble component.
**When to use:** Any AI message that needs structured UI beyond plain text.

### Anti-Patterns to Avoid
- **Inline Persona composition in useChat:** Don't inline the PERSONA block text in `useChat.ts:433`. Use `PersonaInjector.inject()` for testability and single-source-of-truth.
- **LLM-based quick actions:** Don't call an LLM for hostname→action mapping. CONTEXT.md D-31 mandates static mapping for instant, predictable results.
- **Separate PersonaPromptBuilder class:** CONTEXT.md D-13 explicitly rules this out in v7.3. Keep prompt composition as a private method in PersonaInjector.
- **Welcome Cards as a modal/overlay:** CONTEXT.md D-17 mandates inline rendering in the existing empty-state area. Not an overlay or modal.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Prompt template variable interpolation | Custom regex engine | Existing TemplateEngine (`src/core/prompts/TemplateEngine.ts`) | Already handles `{{var}}` replacement, extraction, validation. Welcome Cards use PromptManager which wraps TemplateEngine. |
| User preference persistence | Custom chrome.storage wrapper | Existing UserMemoryStore / chrome.storage.local pattern | `welcomeCardsDismissed` flag follows existing preference patterns. Use UserMemoryStore.upsert() for fact storage or workspaceStore pattern for simple flags. |
| Chip/strip UI for action buttons | Custom flexbox implementation | antd Button `size="small"` + `variant="outlined"` in a Flex container | Handles accessibility, hover states, focus rings, dark mode out of the box. |
| Code block detection in markdown | Custom regex on rendered output | XMarkdown `components` prop — render custom component for `code` fences | XMarkdown already parses markdown AST; `components` prop lets you replace code fence rendering with CodeBlockActions wrapper. |

**Key insight:** This phase adds no fundamentally new infrastructure categories. Everything is either a new UI component using existing antd/@ant-design/x primitives or a new core service following the established class+singleton pattern. The don't-hand-roll items are all already solved by existing project infrastructure.

## Common Pitfalls

### Pitfall 1: Stale Persona in Agent Mode
**What goes wrong:** `PersonaInjector.inject()` is called in AgentOrchestrator once at pipeline start, but persona updates (from Options in future phases) are not reflected until next pipeline invocation.
**Why it happens:** AgentOrchestrator assembles the system prompt during `runWithContext()` and the pipeline may run for multiple rounds. Mid-pipeline persona changes could be missed.
**How to avoid:** CONTEXT.md D-12 mandates per-call injection — every `runWithContext()` call reassembles the system prompt. This is already the default pattern in the current code (AgentOrchestrator.runWithContext line 167-168 calls `buildPlannerPrompt` each invocation). Ensure PersonaInjector reads the persona fresh each call, not cached at construction time.
**Warning signs:** Agent responses using old persona language after Options persona change.

### Pitfall 2: Bubble contentRender Type Conflicts with BubbleListItem
**What goes wrong:** The current `BubbleListItem` interface (useChat.ts:56-66) has `content: string`. Adding clarification/follow-up metadata requires changing content to an object type, which breaks existing `contentRender` assumptions.
**Why it happens:** TypeScript enforces the `content` type throughout the Bubble.List items array.
**How to avoid:** Extend `BubbleListItem` to use a discriminated union or add optional metadata fields (`clarification?: ClarificationPayload`, `followUpSuggestions?: FollowUpSuggestion[]`, `codeBlocks?: CodeBlockMeta[]`) alongside the existing `content: string`. Keep content as string for text messages; metadata fields carry structured UI data.
**Warning signs:** TypeScript errors in ChatPage.tsx Bubble rendering after adding metadata fields.

### Pitfall 3: WelcomeCards Flash on Conversation Switch
**What goes wrong:** When switching conversations, the messages take a moment to load from IndexedDB. During that gap, `messages.length === 0` briefly shows WelcomeCards before messages appear.
**Why it happens:** React state updates are asynchronous; `setMessages([])` happens before `setMessages(loadedMessages)`.
**How to avoid:** Add a `conversationLoading` state flag. Set to `true` in `switchConversation` before loading, set to `false` after messages are loaded. WelcomeCards only render when `messages.length === 0 && !conversationLoading`.
**Warning signs:** Brief Welcome Cards flash when switching between non-empty conversations.

### Pitfall 4: FollowUpService Blocking Stream Display
**What goes wrong:** If `FollowUpService.generateSuggestions()` is awaited before marking the response complete, the user sees a spinner even though the full response has streamed.
**Why it happens:** The stream completion callback blocks on suggestion generation.
**How to avoid:** CONTEXT.md D-30 mandates fire-and-forget async — call `generateSuggestions()` without awaiting, update state when results arrive. Follow the existing `memoryEngine.extract()` pattern (useChat.ts:275-277). Use a 3-second timeout with graceful degradation (no chips on timeout).
**Warning signs:** Response text visible but loading spinner persists for 3+ seconds.

### Pitfall 5: XMarkdown Code Fence Detection for CodeBlockActions
**What goes wrong:** XMarkdown renders code blocks as final DOM, making it hard to attach action buttons to individual code fences.
**Why it happens:** XMarkdown's streaming mode renders incrementally; the final DOM structure may not have stable selectors for code blocks.
**How to avoid:** Use XMarkdown's `components` prop to override code fence rendering:
```tsx
<XMarkdown
  content={item.content}
  components={{
    code: (props) => <CodeBlockActions {...props} />,
  }}
/>
```
This pattern is documented in @ant-design/x XMarkdown's custom component support.
[CITED: https://github.com/ant-design/x/blob/main/packages/x-skill/skills/x-markdown/reference/STREAMING.md]
**Warning signs:** Action buttons appearing on inline code (`backticks`) instead of only code fences.

### PersonaInjector with Structured PERSONA Block
```typescript
// Source: CONTEXT.md D-02, D-03, D-13 — project decisions
export class PersonaInjector {
  constructor(private personaService: PersonaService) {}

  inject(systemPrompt: string, hints?: PersonaHint[]): string {
    const profile = this.personaService.getProfile();
    const personaBlock = this.#buildPersonaBlock(profile, hints);
    return `${personaBlock}\n\n${systemPrompt}`;
  }

  #buildPersonaBlock(profile: PersonaProfile, hints?: PersonaHint[]): string {
    const lines = [
      '## PERSONA',
      '',
      `You are ${profile.identity.name} — ${profile.identity.tagline}.`,
      '',
      '### Core Values',
      ...profile.coreValues.map(v => `- ${v}`),
      '',
      '### Communication Style',
      `- Tone: ${profile.languageStyle.tone}`,
      `- Response style: ${profile.languageStyle.responseStyle}`,
      `- Vocabulary: ${profile.languageStyle.vocabulary}`,
      '',
      '### Behavioral Preferences',
      ...profile.behavioralPreferences.map(p => `- ${p}`),
    ];

    if (hints?.length) {
      lines.push('', '### Context-Specific Guidance');
      for (const hint of hints) {
        lines.push(`- ${hint.instruction}`);
      }
    }

    return lines.join('\n');
  }
}
```
[CITED: CONTEXT.md D-03 — Structured PERSONA block near start of prompt]

### WelcomeCardService with Three-Tier Sorting
```typescript
// Source: CONTEXT.md D-16, D-22 — project decisions
export class WelcomeCardService {
  async getCards(): Promise<WelcomeCard[]> {
    const templates = await promptManager.getAllTemplates();
    const hostname = workspaceStore.getState().currentPageContext?.hostname;

    // Tier 1: Usage history from UserMemoryStore
    const usageScores = await this.#getUsageScores();

    // Tier 2: Contextual boost from hostname
    const contextualBoosts = hostname ? this.#getHostnameBoost(hostname) : {};

    // Tier 3: Default curated order
    const cards = CURATED_CAPABILITY_CARDS.map((card, i) => ({
      ...card,
      score: (usageScores[card.id] ?? 0) + (contextualBoosts[card.id] ?? 0) + (100 - i),
    }));

    return cards.sort((a, b) => b.score - a.score);
  }

  #getHostnameBoost(hostname: string): Record<string, number> {
    const mapping: Record<string, Record<string, number>> = {
      'servicenow.com': { summarize: 50, research: 30 },
      'github.com': { explain_code: 50, write_script: 30 },
    };
    for (const [pattern, boosts] of Object.entries(mapping)) {
      if (hostname.includes(pattern)) return boosts;
    }
    return {};
  }
}
```
[CITED: CONTEXT.md D-16, D-22]

## Open Questions

1. **FollowUpService Haiku-tier model selection**
   - What we know: CONTEXT.md D-27 specifies "Haiku-tier call (max ~30 tokens, non-blocking, 3s timeout)". ProviderRouter exists for model selection.
   - What's unclear: Whether to use a dedicated model config or reuse the active provider's Haiku model. The useChat.send() method passes `workspaceActiveProvider` — FollowUpService may need its own provider resolution.
   - Recommendation: Follow the `generateTitle` pattern (useChat.ts:93-119) which makes a separate lightweight LLM call. Use ProviderRouter with explicit 'haiku' tier.

2. **CodeBlockActions "Insert into page" detection**
   - What we know: CONTEXT.md says "Only shown when ServiceNow page has active textarea". The content script detects page context but not editable fields.
   - What's unclear: How to detect editable textareas on the pinned ServiceNow page. Content scripts are extraction-only in v0.1 per STATE.md decision.
   - Recommendation: In v7.3, always show the Insert button but disable it with tooltip "No editable text area detected on the current page". Active textarea detection is deferred to Phase 7.5.

3. **Stage indicator event emission in Chat mode**
   - What we know: useChat uses `AgentOrchestrator.runWithContext()` which yields OrchestratorEvent types. The pipeline has stages: ContextOptimizer → PlannerService → RendererService.
   - What's unclear: Whether the current OrchestratorEvent types include stage-start events. Currently, events are `plan-created`, `tool-called`, `tool-result`, `text-delta`, `text-complete`, `error`, `context-degraded`, `context-error`, `waiting-permission`.
   - Recommendation: Add three new OrchestratorEvent types: `stage-start` (with stage: 'context' | 'planning' | 'generating') and `stage-end`. Emit from useChat.send() setStage() calls that already exist (line 413 `setStage('retrieving')`).
