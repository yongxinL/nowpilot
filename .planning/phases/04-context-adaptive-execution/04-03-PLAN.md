<objective>
Create the ContextCompressor module — an injectable service that compresses conversation history and page/case context. Per D-03, history compression uses LLM-based summarization for medium/large tiers (cost justified by budget) and heuristic character-based truncation for tiny/small tiers. Page/case context always uses heuristic/structural extraction since it's already structured data.

Purpose: Provide ContextOptimizer with compression strategies it can invoke during the degradation pipeline. Following D-04, ContextCompressor is a standalone class+singleton injected into ContextOptimizer's constructor.
Output: ContextCompressor class + singleton + test file with mocked LLM calls.
</objective>

  <action>
Create `src/core/context/ContextCompressor.ts` following the AgentOrchestrator constructor DI pattern:

1. **Type for model accessor**: `type ModelAccessor = (providerId: string, modelId: string) => Promise<unknown>` — lightweight accessor, not full ProviderRouter. ContextCompressor just needs a model instance for `generateText` calls.

2. **ContextCompressor class** with constructor DI:
   ```
   constructor(private modelAccessor: ModelAccessor) {}
   ```
   Follow RESEARCH.md Open Question #1: use a lightweight model accessor callback, not the full ProviderRouter.

3. **compressHistory(messages, tier, providerId, modelId): Promise<string>** — Per D-03:
   - **medium/large tiers**: LLM summarization path:
     - Map messages to `{role}-{content}\n` format
     - Call `generateText` from 'ai' with the summary prompt (below), `maxTokens: 200`, `temperature: 0`
     - Return the summarized text
   - **tiny/small tiers**: Heuristic truncation path:
     - Concatenate messages
     - Estimate tokens via `tokenEstimator` (import the singleton)
     - If over 500 estimated tokens, truncate to last ~500 tokens worth of chars (CharCount = 500 * 4 for Latin, * 3 for CJK)
     - Return truncated text
   - Handle errors gracefully: if LLM call fails, fall back to heuristic truncation (never throw — degradation pipeline must keep moving per Pitfall 3)

4. **compressContext(pageContext: string | Record<string, unknown>): string** — Per D-03 (heuristic ALWAYS for page/case context):
   - If pageContext is an object, extract structured fields: `title`, `url`, `summary` or similar top-level keys
   - If pageContext is a string, apply character-based truncation to ~300 estimated tokens
   - Return the compressed context string

5. **SUMMARY_PROMPT** — Module-level constant per RESEARCH.md:
   ```
   const HISTORY_SUMMARY_PROMPT = `Summarize the following conversation in at most 200 tokens. Focus on: key decisions, action items, and user preferences. Do not include greetings or pleasantries.

   Conversation:
   {history}

   Summary:`;
   ```

6. **Private helper: heuristicTruncate(text: string, maxTokens: number): string** — Char-based truncation using tokenEstimator.estimateTokens() to find the cutoff point.

7. **Singleton export**: `export const contextCompressor = new ContextCompressor(getModelForCompression);` where `getModelForCompression` is a placeholder that the wiring layer replaces. In tests, the singleton isn't used — tests create their own instances with mocked accessor.

8. **debugLog integration**: Log compression method used, token counts before/after. Prefix: `[ContextCompressor]`. HARD-09: all catch blocks call debugLog.

9. **No ProviderRouter dependency** — ContextCompressor receives a simple callback. This avoids coupling the compressor to the main pipeline's routing concerns (circuit breakers, retries are overkill for a side-summarization call).
