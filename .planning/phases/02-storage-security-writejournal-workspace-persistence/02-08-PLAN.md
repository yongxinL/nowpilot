<objective>
Fix CR-01 (BLOCKER, from 02-VERIFICATION.md truth 1 / 02-REVIEW.md CRITICAL-01): boot recovery reconstructs `np_workspace` from metadata-only journal-entry fields, overwriting the real value with `{"workspaceId":"","conversationId":null}` on every crash recovery.

Purpose: The boot `recoverJournal` replay in `entrypoints/sidepanel/main.tsx:75-78` and `entrypoints/standalone/main.tsx:76-77` builds the recovery value from `entry.workspaceId ?? ''` / `entry.conversationId ?? null`, but `WriteJournalEntry` (src/types/storage.ts:63-70) is metadata-only — those fields never exist. The `?? ''` / `?? null` fallbacks always fire, so any boot with a pending/applying update-workspace entry OVERWRITES the real `np_workspace` — data loss on the exact crash-recovery path. Two compounding defects are fixed here: (a) the value is reconstructed from fields that never exist, and (b) `update-workspace` journal steps are never registered in production, so `isSupportedOperation` returns false and recovery silently skips. The fix extracts a shared, testable `recoverWorkspaceJournal` helper that registers the steps and re-applies the CURRENT `np_workspace` value from storage (option (b) from VERIFICATION.md `missing`), and wires both entrypoints to it.

Output:
  - `recoverWorkspaceJournal(deps)` in `src/core/storage/WriteJournal.ts` — the real boot-recovery path.
  - Both entrypoints call it and pass the real `getWorkspaceId` into `startElection`.
  - Corrected `WorkspacePersistence.test.ts` Test 5 and `WriteJournal.test.ts` Test 1 that drive `recoverWorkspaceJournal` with a metadata-only entry + real current value and assert retention.
</objective>
