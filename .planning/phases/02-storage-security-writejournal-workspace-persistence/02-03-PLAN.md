<objective>
Deliver the AES-GCM at-rest vault (STORAGE-03): `EncryptedStorage` as the crypto primitive (per-key 16-byte salt + 12-byte IV, PBKDF2-derived AES-GCM-256 keys per §15.2) and `KeyVault` as the installSecret lifecycle + PROVIDER_KEY_UNREADABLE state machine (D-02/D-04). Prove the vault-roundtrip and cross-install fixture scenarios (D-20/21) with unit tests.

Purpose: Provider API keys must never sit in plaintext in chrome.storage. The vault is AT-REST OBFUSCATION, install-bound, never exported (D-01/D-02) — frame it that way in comments; never over-claim a user-secret boundary.
Output: EncryptedStorage + KeyVault + their tests; `np_install_secret` lifecycle established for the phase.

Flagged assumptions (specless probe):
- A-04 (carried): PBKDF2 100k iterations stay locked (D-02) despite OWASP 2023 recommending >= 600k — flagged in RESEARCH as informational v0.2 hardening, not a Phase-2 change.
- A-07: crypto.subtle is available in all Side Panel/Standalone contexts (verified in jsdom-align AND MV3); R-3 confines the vault to panels — the background SW never imports KeyVault.
- A-08: chrome.runtime.id is stable per install and never changes on browser update — if it ever did, the design's own PROVIDER_KEY_UNREADABLE recovery path covers it (RESEARCH A3).
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| plaintext secret ↔ EncryptedStorage | Secrets enter/leave the crypto boundary here — the ONLY place plaintext exists |
| chrome.storage.local np_install_secret / ciphertext | At-rest values a disk/backup/sync inspection could read |
| KeyVault state → ProviderRegistry gate | Unreadable provider state drives the onboarding 'configure later' routing |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-2-03-01 | Information Disclosure | EncryptedStorage plaintext keys | high | mitigate | Secrets exist in plaintext only transiently inside encrypt/decrypt (never persisted, never logged); ciphertext + installSecret are the only at-rest forms; R-3 confines the vault to panels; the background SW never imports KeyVault/EncryptedStorage (isolation check extended in 02-11). |
| T-2-03-02 | Tampering | installSecret regeneration/clobber | critical | mitigate | read-then-write-if-absent + immutable-once-set (D-02) — the cross-install test proves a second instance never regenerates; no auto-regenerate path exists anywhere (grep-gated: only wipeProviderKey deletes ciphertext, user-initiated). |
| T-2-03-03 | Information Disclosure | decrypt failure auto-wipe | high | mitigate | decryptSecret maps VAULT_DECRYPT_FAILED → PROVIDER_KEY_UNREADABLE state; NO code path deletes ciphertext on failure (test case 2 asserts ciphertext survives cross-install) (D-04). |
| T-2-03-04 | Information Disclosure | installSecret in sync/exports | high | mitigate | np_install_secret is written ONLY to chrome.storage.local (D-02); export (02-09) excludes np_install_secret + np_providers explicitly; no code writes it to sync or any export (02-09 acceptance greps prove exclusion). |
| T-2-03-05 | Elevation of Privilege | KeyVault singleton state leakage across contexts | medium | mitigate | One shared PROVIDER_KEY_UNREADABLE state (D-04) means a degraded provider in one panel converges to the same gate in the other; no per-context divergent state is modeled. |
