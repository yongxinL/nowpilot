# Phase 2 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Phase scope — this is NOT a UI-building phase.** Phase 2 is the storage, security, WriteJournal and workspace-persistence foundation. `02-CONTEXT.md` D2-18 states "Do not redesign the Chat interface in Phase 2"; D2-20 excludes "final Chat UI integration and visual acceptance". This document therefore **adds no new visual language, no new token, no new spacing value, no new type size and no new component**. It locks the existing approved design-system contracts for the four UI-adjacent surfaces Phase 2 touches, and states explicitly where a surface has **no** new design decision.

**Precedence.** On any conflict: `PRODUCT_SPEC.md` wins for functional rules → `DESIGN_SYSTEM.md` §8 written metrics win over a stale annotated image → `01-UI-SPEC.md` wins for every shell, surface metric, token and Phase-1 string it already pins → this document wins only for the four surfaces listed below. Where this document is silent, `01-UI-SPEC.md` is the contract, unchanged.

**The four UI-adjacent surfaces in Phase 2 (and nothing else):**

| # | Surface | New design decision? |
|---|---------|----------------------|
| 1 | Conversation-area hydration states (`idle` · `hydrating` · `ready` · `empty` · `failed` · `recovery required`, D2-18) | **Yes** — which existing approved presentation each state may render, and which it must not |
| 2 | `MirrorBanner` activation through authoritative writer-election state (D-12 carry-forward) | **Yes** — activation condition and canonical copy. Visual treatment is **unchanged** (Phase 15 owns final copy/visual treatment) |
| 3 | Phase-2 credential capability notice (D2-02) | **Yes** — copy, tone and placement |
| 4 | Storage-failure / degraded-mode notification path (`IDB_BLOCKED` §19.10, `IDB_MIGRATION_FAILED` §20.4, election failure §20.11) | **Yes** — vehicle and copy |

**Explicitly out of scope (no design decision is made here):** the Chat canvas layout, the composer, the Sider, the command palette, the theme contract, the onboarding steps' structure, Notes/Options/Tools/Write pages, chat-history list surfaces, message bubbles and action sets. All remain exactly as `01-UI-SPEC.md` pins them. No `data-np-backing` marker is added, moved or removed by this document.

### String ownership rules (Phase 2)

- `chat.empty` / `chat.emptyBody` keep their Phase-1 meaning: the **conversation canvas** has no messages. They are **not** the storage-empty string.
- `No conversations yet` and `Skeleton shimmer` appear in `PRODUCT_SPEC` §12 only as the `ChatHistoryDB load` row's Empty and Loading cells. `No conversations yet` belongs to the **chat-history list** surface (FLOW-17, Phase 15) — **Phase 2 does not render it**, and does not add a key for it.
- `chat.loading` (`Connecting to provider...`) and `chat.errorRetry` (`Provider error. [Retry] [Switch Provider]`) are **provider** states owned by Phase 3. Phase 2 must not render them: no provider request occurs in Phase 2.
- `deferred.reasonFixture` / `deferred.reasonDeferred` / `deferred.phaseBody` stay owned by `DeferredNotice`. The capability notice does not reuse them.

### Forbidden claims (hard rule — D2-02, extended)

These strings must **not** appear in Phase 2 UI unless the corresponding **production** operation actually completed. In Phase 2 none of them can:

1. **`Credential stored`** — the onboarding credential value stays in component memory only and never reaches `CredentialStorePort` (D2-01, D2-02).
2. **`Provider connected`** — no provider request occurs in Phase 2.
3. **`Provider validated`** — fixture validation is not provider validation.
4. **`Provider ready`** — provider runtime readiness is Phase 3.
5. **Any migration-completion claim** — `History migrated`, `Conversations restored`, `Setup complete` and equivalents. Migration is **silent**; its only permitted user-visible output is the failure notice in the table above.
6. **Any persistence-success claim for an unverified write** — no `Saved`, no `Synced`, no success toast, until the destination read-back has verified the write (D2-10 step 7, D2-14).
7. **Any election, writer-identity, epoch, demotion or mirroring claim not backed by authoritative election state** (D-12). The `MirrorBanner` renders **only** on the `mirror` state; it never renders because Standalone merely opened.
8. **Phase 1's existing prohibitions, unchanged** — no green health dot, no fake provider name, no fake model list, no simulated stream, no timer-driven success, no fixture value presented as user data.
9. **No diagnostic leakage in any user-visible string** — no operation ID, storage key, journal stage name, record ID, file path, error code, ciphertext, or message/note body text (D2-11, D2-13, D2-16).

## Phase 2 UI Surface Contracts

### 1. Conversation-area hydration states (D2-17, D2-18)

The chat store exposes one explicit hydration status. Components consume it through the **existing** store contract; they do not access IndexedDB, construct transactions, read legacy `np_store`, manipulate the journal, or decide migration state (D2-20).

| Hydration status | Conversation-area presentation | Prohibitions |
|---|---|---|
| `idle` | The shell's own pre-hydration content. **No hydration-dependent claim is made.** | Must not render the empty presentation or a ready presentation |
| `hydrating` | AntD **`Skeleton`** filling the conversation region | Must not render `chat.empty`, `chat.emptyBody`, or any error presentation |
| `ready` | The hydrated projection, unchanged from the existing approved presentation | — |
| `empty` | The existing approved empty presentation: `chat.empty` + `chat.emptyBody` | Must not render before hydration completes |
| `failed` | Inline error: `storage.hydrationFailed` + `common.retry` | No legacy message-body fallback; no empty presentation; no silent empty history |
| `recovery required` | Same inline error presentation as `failed`, with `common.retry` re-attempting recovery | Same prohibitions. Must not present as `empty`, and must not discard recoverable journal state |

**Cross-cutting rules for this surface:**

- A database error is **never** rendered as an empty conversation history (D2-18).
- One malformed conversation follows the partial-failure policy: the record is identified by safe ID only, is never silently deleted, and never logs body text (D2-20).
- The composer, header, status bar and toolbar are **unchanged** by hydration status. Only the conversation region varies.
- No new `data-np-backing` marker is added: hydration states are **live** behaviour, and a marker on a live region is a defect (Phase-1 hard rule 5).

### 2. `MirrorBanner` activation (D-12 carry-forward, D2-34)

`MirrorBanner` is the **single** surface that reports cross-surface writer state. It is activated by **authoritative election state only** — never by the fact that Standalone opened.

| Authoritative state | Banner? | Copy |
|---|---|---|
| `primary` | **No** | — |
| `mirror` | **Yes** | `workspace.mirroringNotice` + `workspace.mirrorRefocus` |
| `election-pending` | **No** | No approved copy exists; the state is transient (3 s heartbeat, 2 missed → re-election). The surface must not claim an election outcome it does not have |
| `handoff-pending` | **No** | The existing handoff-pending treatment (`workspace.handoffPending`) already owns this state |
| `handoff-failed` | **No** | The existing `standalone.openFailed` + `Retry` path already owns this state |
| `writer-unavailable` | **No** | No approved copy exists. The surface keeps its last authoritative state and reports nothing it does not know |
| Election error (`ELECTION_TIMEOUT` / `WORKSPACE_STORAGE_UNAVAILABLE`) | **No** | Routes to the persistent notification path (surface 4) |

**Interaction contract:**

- The banner renders at most once per surface, above the conversation region, in the existing banner slot.
- **Visual treatment is unchanged and is not a Phase-2 decision** — the shipped contract stands: 32px `min-height`, full width, `colorPrimaryBg` background, hairline `colorBorderSecondary` top and bottom, 12px caption (`colorTextBase`), 12px action (`colorPrimary`, underlined), `padding: 0 16px`. Phase 15 owns final copy and visual treatment; Phase 2 changes only the **activation condition** and replaces the inline literal caption with the canonical key.
- `role="status"` + `aria-live="polite"` stay on the banner (state changes announce politely).
- The action is a real control with the accessible name `workspace.mirrorRefocusA11y`; it is keyboard-reachable and carries the visible label `Refocus here`.
- **No optimistic state change.** The banner stays mounted and unchanged until authoritative election state reports `primary`. It never hides on click, never shows a success toast, and never claims a promotion that the election has not acknowledged. A refocus that does not reach `primary` surfaces `workspace.electionFailed` through the notification path.
- The current inline literal `Switched to Standalone.` is a **defect** and is replaced by `t('workspace.mirroringNotice')`. The current inline `aria-label` literal is replaced by `t('workspace.mirrorRefocusA11y')`.

### 3. Phase-2 credential capability notice (D2-02)

- **One notice, one place:** an AntD `Alert type="info"` `showIcon` rendered on the onboarding credential step (step 3), below the existing fixture-marked credential field group.
- **Copy:** `t('storage.credentialCapability')` — the D2-02 sentence, verbatim. No paraphrase, no second sentence, no interpolation.
- **Non-interactive:** no action button, no link, no dismiss control, no tooltip-only detail. It is a statement, not an affordance.
- **Not a `DeferredNotice`:** it carries **no** `data-np-backing` attribute and does not reuse `deferred.*` copy — see `## Color` for why the tone is `colorInfo`.
- **No credential echo:** the notice never reflects the field's value, its length, whether it is populated, or whether anything was stored. It states a capability, not an outcome.
- **Options credential controls** stay `disabled` + `data-np-backing="deferred"` exactly as `01-UI-SPEC.md` pins them. Phase 2 does not re-mark, re-enable or re-word them, and adds no notice to Options.

### 4. Storage-failure and degraded-mode notification path

Phase 2 is the first phase to use the acknowledgement-requiring notification path. All three Phase-2 failure notices share one vehicle.

| Failure | Vehicle | Copy | Action |
|---|---|---|---|
| IndexedDB unavailable / blocked (`IDB_BLOCKED`, §19.10) | `notification.error({ duration: 0 })` | `storage.degraded` | none — the surface degrades to in-memory and stays usable |
| Migration failure (`IDB_MIGRATION_FAILED`, §20.4) | `notification.error({ duration: 0 })` | `storage.migrationFailed` | none — the source data is preserved and a retry is automatic |
| Election / refocus failure (§20.11) | `notification.error({ duration: 0 })` | `workspace.electionFailed` | `Reload` (`shell.errorReload`) |

**Cross-cutting rules:**

- All calls go through `App.useApp()`. Static `notification.*` imports remain forbidden.
- `duration: 0` for all three — they require acknowledgement (§17.4).
- Each notice uses a **stable `key`** so a repeated failure updates one notification rather than stacking.
- Notices contain **no** record content, body text, identifiers, file paths, storage keys, journal stage names or error codes (D2-11, D2-13, D2-16).
- A notice is never the only affordance for a required action, and never blocks the surface.

**Carried-forward Phase-1 prerequisite (not a new design decision).** `01-UI-SPEC.md` § Toast / notification configuration pins `message.config({ maxCount: 3, duration: 5 })` as **required in Phase 1**, and errors that require acknowledgement as `notification.error({ duration: 0 })`. A repo-wide scan of `src/` finds **no** `message.config` / `notification.config` call — the pinned cap is not wired. Phase 2 is the first phase to depend on this path, so wiring the pinned configuration at each surface root is a Phase-2 prerequisite. It adds no design decision; the values are already pinned.
