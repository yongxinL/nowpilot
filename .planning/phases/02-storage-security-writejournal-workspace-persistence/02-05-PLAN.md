The redacted failure store and the one-time legacy chat migration: move prototype message bodies out of `np_store` into ChatHistoryDB, then sanitise the source — journaled, idempotent, restart-safe.

Purpose: this is the phase's one-way data migration (D2-07/D2-17) and the reason no message body may remain in `chrome.storage`. `ErrorStore` lands here because §20.4's `IDB_MIGRATION_FAILED` recording is its first real consumer.
Output: `ErrorStore` with its bounded redacted contract, `legacyChatMigration` with all seven stages and the per-conversation procedure, and the D2-15 case table as an executable suite.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Legacy `np_store` blob → migration | The stored blob is prototype-era data of unknown shape and may be malformed or hostile. |
| Migration → destination | A partial write followed by a crash must not lose data or produce duplicates. |
| Failure → ErrorStore | Failure records are durable and must carry no body, credential or raw exception payload. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-23 | Information Disclosure | sanitised source | high | mitigate | Sanitisation rewrites the source from an allow-list after a verified read-back; the suite asserts the sentinel body and the excerpt field are absent from every storage map and the log buffer. |
| T-02-24 | Information Disclosure | body-derived fields | high | mitigate | The excerpt field is treated as a body (dropped) and the title as metadata (moved to the conversation index); the suite asserts both explicitly. |
| T-02-25 | Tampering | replay duplication | high | mitigate | Deterministic destination keys plus the journal idempotency key; duplicate-run and already-migrated cases assert counts. |
| T-02-26 | Data loss | sanitisation before verification | critical | mitigate | Sanitisation runs only after `destination-verified`; the failure cases assert the source record stays intact and the entry stays non-terminal. |
| T-02-27 | Repudiation | quarantined records | medium | mitigate | Unsupported records are quarantined by safe id with a redacted failure record; no discard path exists and D2-13's discard checkpoint is explicitly not taken. |
| T-02-28 | Denial of Service | unbounded error growth | medium | mitigate | `ERROR_STORE_MAX_RECORDS = 100` FIFO plus cleanup of old resolved records; the bound is asserted. |
| T-02-29 | Elevation of Privilege | cross-store atomicity assumption | medium | mitigate | No shared transaction is attempted; correctness rests on stages, idempotency and read-back, and the plan states the prohibition explicitly. |
| T-02-SC | Tampering | npm installs | high | mitigate | No install in this plan. |
</threat_model>
