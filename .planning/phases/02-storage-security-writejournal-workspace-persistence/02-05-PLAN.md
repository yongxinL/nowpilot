<objective>
Create the WriteJournal coordinator system — the WriteJournalEntry type with Zod validation, and the WriteJournal class with journaling, recovery, and pruning. Implements D-01 through D-06.

Purpose: Multi-store operations (IndexedDB + chrome.storage.local) cannot be atomic. The WriteJournal ensures that after a crash or interruption, pending operations are replayed idempotently to reach a consistent state. This is the correctness backbone of the entire storage layer.

Output: `src/core/storage/WriteJournalEntry.ts` with types + Zod schema, `src/core/storage/WriteJournal.ts` with coordinator class, plus tests for the full entry lifecycle and recovery.
</objective>

    Create `src/core/storage/WriteJournal.ts`. Implements the journal coordinator per D-01 through D-06. Class + singleton export pattern.

    CONCRETE IMPLEMENTATION REQUIREMENTS:

    1. Import `{ debugLog }` from `'../utils/debugLog'`.
    2. Import `{ getDB }` from `'./IndexedDBManager'`.
    3. Import type `{ WriteJournalEntry, WriteJournalOperation, WriteJournalSteps }` from `'./WriteJournalEntry'`.
    4. Import `{ validateWriteJournalEntry }` from `'./WriteJournalEntry'`.

    5. Export class `WriteJournal`:
       - `private readonly RETENTION_MS = 7 * 24 * 60 * 60 * 1000` (7 days per D-06)
       - `private readonly MAX_COMPLETED_ENTRIES = 1000` (per D-06)

    6. Method `async begin(operation: WriteJournalOperation, targetIds: Record<string, string>, steps: { name: string }[]): Promise<WriteJournalEntry>` — per D-01, D-05:
       a. Generate UUID: `const id = crypto.randomUUID()`.
       b. Create entry object:
          ```typescript
          const entry: WriteJournalEntry = {
            id, operation, status: 'pending',
            createdAt: Date.now(), updatedAt: Date.now(),
            attempts: 0,
            targetIds,
            steps: steps.map(s => ({ name: s.name, status: 'pending' as const })),
          };
          ```
       c. Validate: `validateWriteJournalEntry(entry)`.
       d. **Separate transaction (D-05):** Get the DB, then `const tx = db.transaction('write_journal_entries', 'readwrite')`. `await tx.store.put(entry)`. `await tx.done`.
       e. `debugLog('debug', 'WriteJournal: entry created', { id, operation })`.
       f. Return entry.

    7. Method `async markStepStart(entryId: string, stepIndex: number): Promise<void>`:
       a. Get the journal store. Read entry by `entryId`.
       b. If entry exists, update `entry.status` to `'applying'` (if not already), update the step at `stepIndex` to `{ ...step, status: 'pending' }` (no change needed if it's the start), and `entry.updatedAt = Date.now()`.
       c. Put back and await transaction.

    8. Method `async markStepComplete(entryId: string, stepIndex: number): Promise<void>`:
       a. Read entry. If found:
          - Set `entry.steps[stepIndex].status = 'completed'`.
          - Increment `entry.attempts` by 1.
          - `entry.updatedAt = Date.now()`.
       b. Put back and await transaction.

    9. Method `async markStepFailed(entryId: string, stepIndex: number, errorMessage: string): Promise<void>`:
       a. Read entry. If found:
          - Set `entry.steps[stepIndex].status = 'failed'`.
          - Set `entry.steps[stepIndex].error = errorMessage`.
          - `entry.updatedAt = Date.now()`.
       b. Put back and await transaction.

    10. Method `async markCompleted(entryId: string): Promise<void>` — per D-04:
        a. Read entry. Set `entry.status = 'completed'`, `entry.updatedAt = Date.now()`.
        b. Put back and await transaction.
        c. `debugLog('debug', 'WriteJournal: entry completed', { id: entryId })`.

    11. Method `async markFailed(entryId: string): Promise<void>` — per D-04:
        a. Read entry. Set `entry.status = 'failed'`, `entry.updatedAt = Date.now()`.
        b. Put back and await transaction.
        c. `debugLog('error', 'WriteJournal: entry failed', { id: entryId })`.

    12. Method `async recover(): Promise<number>` — per D-02, D-03:
        a. Get the DB. Get all entries from `write_journal_entries` using the `by-status` index where status is `'pending'` OR `'applying'` (query both).
        b. Let `recoveredCount = 0`.
        c. For each entry:
           - (D-03 idempotency check): For each `targetId` in `entry.targetIds` (store → key), check if the target store already contains that key. If the data already exists, skip this entry and mark it `completed` — it was already applied before the crash.
           - For each step in `entry.steps` where `step.status === 'pending'` or `'failed'`:
             - Set `step.status = 'pending'` and `entry.status = 'applying'`.
             - Mark entry as `completed` if all steps are already done.
             - (`<!-- planner-discipline-allow: LIT -->` Replaying means the caller is expected to re-execute the actual data operation. The journal records the outcome.)
           - Increment `recoveredCount`.
        d. Log: `debugLog('info', 'WriteJournal: recovery complete', { recovered: recoveredCount })`.
        e. Return `recoveredCount`.

    13. Method `async prune(): Promise<number>` — per D-06:
        a. Get all entries sorted by `createdAt` descending.
        b. Count completed entries older than `RETENTION_MS`: `entry.createdAt < (Date.now() - this.RETENTION_MS)`.
        c. If completed entries exceed `MAX_COMPLETED_ENTRIES`, delete the oldest ones, keeping the most recent `MAX_COMPLETED_ENTRIES`.
        d. For each entry to delete: `db.delete('write_journal_entries', entry.id)`.
        e. Return count of pruned entries.
        f. Note: pending, applying, failed, and rolled-back entries are NEVER pruned per D-06.

    14. Export singleton: `export const writeJournal = new WriteJournal()`.

    15. Run `npx tsc --noEmit` to verify compilation.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| WriteJournal → IndexedDB (write_journal_entries) | Journal entries persist in IndexedDB — durability depends on browser storage |
| WriteJournal.begin() → target data stores | Journal entry committed BEFORE data write per D-05 — crash between journal and data write is recoverable |
| WriteJournal.recover() → IndexedDB queries | Recovery reads journal entries and checks target stores for idempotency |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-07 | Tampering | `WriteJournal.recover()` — replaying already-applied entries | medium | mitigate | Per D-03: idempotency check via UUID in `targetIds`. Before replaying any step, query target store for matching data. If found, skip and mark `completed`. |
| T-02-08 | Information Disclosure | `WriteJournal` — journal entries exposing sensitive data | low | accept | Journal entries only contain operation metadata (operation type, target IDs, status). No message bodies, API keys, or plaintext stored per STOR-07. |
| T-02-09 | Denial of Service | `WriteJournal` — unbounded journal growth | medium | mitigate | Per D-06: `prune()` removes completed entries older than 7 days, capped at 1000 max. Non-completed entries retained indefinitely (diagnostic value). |
| T-02-SC | Tampering | npm/pip/cargo | high | mitigate | No new packages; `crypto.randomUUID()` is built-in. |
</threat_model>
