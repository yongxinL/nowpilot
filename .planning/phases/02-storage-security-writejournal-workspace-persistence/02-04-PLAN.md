<objective>
Create the IndexedDBMigrator class with a migration registry and the v1 initial schema migration. Implements D-09 (versioned, idempotent migrations — running the same migration twice produces the same result) and D-08 (single version counter with unified upgrades).

Purpose: Schema changes must be deterministic and repeatable. The migrator ensures that on each DB version bump, only the necessary migrations run, and re-running them is safe.

Output: `src/core/storage/IndexedDBMigrator.ts` with migration registry and boot(), `src/core/storage/migrations/v1-initial-schema.ts` with the v1 migration, plus tests verifying idempotency.
</objective>

    CONCRETE IMPLEMENTATION REQUIREMENTS:

    1. Import `debugLog` from `'../utils/debugLog'`.
    2. Import `type { NowPilotDB }` from `'./IndexedDBManager'` for type reference (no runtime dependency).

    3. Export interface `IndexedDBMigration`:
       - `fromVersion: number`
       - `toVersion: number`
       - `description: string`
       - `migrate(db: IDBPDatabase<NowPilotDB>, oldVersion: number, newVersion: number): Promise<void>` — note: uses `oldVersion`/`newVersion` params rather than a transaction for simplicity (the migration runs inside idb's upgrade callback where a transaction is already active).

    4. Export class `IndexedDBMigrator`:
       - `private migrations = new Map<number, IndexedDBMigration>()` — keyed by `toVersion`

    5. Method `register(migration: IndexedDBMigration): void`:
       - Check: if `this.migrations.has(migration.toVersion)`, throw `new Error('Migration for version ${migration.toVersion} is already registered')`.
       - Otherwise: `this.migrations.set(migration.toVersion, migration)`.

    6. Method `getMigrationsBetween(fromVersion: number, toVersion: number): IndexedDBMigration[]`:
       - Return all migrations where `m.fromVersion <= fromVersion && m.toVersion <= toVersion`, sorted ascending by `toVersion`. This is the set of migrations that need to run when upgrading from `fromVersion` to `toVersion`.

    7. Method `getAllMigrations(): IndexedDBMigration[]`:
       - Return `Array.from(this.migrations.values()).sort((a, b) => a.toVersion - b.toVersion)`.

    8. Method `async boot(): Promise<void>`:
       - Stub implementation for now — logs `debugLog('info', 'IndexedDBMigrator: boot started')`. The actual migration execution happens inside the IndexedDBManager's upgrade callback using `getMigrationsBetween()`. The `boot()` method is called at app startup to register all migrations before any DB open.

    9. Export singleton: `export const indexedDBMigrator = new IndexedDBMigrator()`.

    10. Run `npx tsc --noEmit` to verify compilation.
  </action>

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-05 | Tampering | `IndexedDBMigrator` — migration runs twice non-idempotently | medium | mitigate | Per D-09: `migrationV1.migrate()` guards with `if (oldVersion >= 1) return`. The idb upgrade callback already provides an atomic versionchange transaction — if migration fails, version is not incremented. |
| T-02-06 | Denial of Service | `IndexedDBMigrator` — migration throws unhandled error | medium | mitigate | Errors in migration are caught by idb's upgrade transaction, which aborts the version change. ErrorStore logging planned for future version. |
| T-02-SC | Tampering | npm/pip/cargo | high | mitigate | No new packages; idb already audited in Plan 01. |
</threat_model>
