# Phase 1 — File-Level Migration Inventory (D-04)

**Artifact:** `.planning/phases/01-mv3-wxt-runtime-antd-shells-workspace/01-MIGRATION-INVENTORY.md`
**Authority:** D-04 (`01-CONTEXT.md`). This is the authoritative file-level conversion map for Phase 1. It is produced and validated **before** executable implementation plans run.
**Consumer rule:** Phase 1 plans reference these rows by `Current path` (or by `Target canonical path` for rows whose current path is `—`). Plans do not duplicate this table. Where a plan and a row disagree, the row wins until the change is recorded through `## Change control`.
**Source discipline:** the row set was enumerated with `git ls-files src entrypoints tests scripts` plus the explicitly named root config files — never a working-tree scan — so generated, ignored and untracked trees cannot leak into the audit.
**Classification rule in force (D-01):** KEEP only when the module already satisfies canonical ownership, responsibility, API, validation, lifecycle, naming and security contracts; ADAPT when concept and most behaviour are correct but path, types, API, validation or responsibility boundary differs; REPLACE when the implementation conflicts with an authoritative contract (workspace-writer election, background responsibilities, runtime-envelope validation, storage ownership, Chrome MV3 lifecycle, provider/MCP execution boundaries, content-script isolation); REMOVE only when duplicated, obsolete, unused, or an incompatible ordinary web-app / generated-server assumption. Canonical specification and accepted ADRs override prototype names and behaviour.
**Row conventions:** `—` marks a cell with no value (a file that does not yet exist, a test with no dedicated suite, an inert status, an inapplicable owner). New canonical files with no prototype counterpart carry `—` as their `Current path`. `Implementation status` and `Verification status` are `pending` until a plan completes its row (downstream plans reconcile them; plans `01-11`, `01-12` and `01-13` update statuses as their work lands).
**Generated-tree exclusion:** `.wxt/**`, `.output/**` and the `dist` symlink are **generated mirrors** — they are never pattern origins, analogs or target paths, and they are excluded from the row set. See `## Explicitly excluded`.

## Change control

The classifications in this inventory are **frozen** once the freeze commit lands. The executor must not invent, extend or silently change them; where a plan and a row disagree, the row is authoritative until the change below is recorded.

Any change made during implementation must be recorded in this file, against the affected row, with all six fields:

1. **Previous classification** — the frozen `KEEP` / `ADAPT` / `REPLACE` / `REMOVE` value.
2. **Replacement classification** — the new value.
3. **Reason** — why the frozen classification could not be honoured.
4. **Affected requirement or contract** — the requirement ID and the governing architecture/design contract that the change touches.
5. **Affected plan** — the plan id whose work the change lands in.
6. **Verification impact** — what the verifier must re-check because of the change, including any test or gate that must be added, re-pointed or retired.

Where a classification changes, the row also records whether its `Target canonical path` changed as a result, and the previous target path is kept in the record.

Material architecture changes — a new module boundary, a changed `srcDir` layout, a changed ownership boundary between surfaces, background or storage, or any deviation from a locked decision in `01-CONTEXT.md` — are **not** self-approved by the executor. They are surfaced to the operator for review before implementation continues, and are recorded here once reviewed.

Status cells may be updated by any plan as its work completes (`pending` → `implemented` → `verified`); a status change does not require the six-field record unless the classification, target path or responsibility also changes.
