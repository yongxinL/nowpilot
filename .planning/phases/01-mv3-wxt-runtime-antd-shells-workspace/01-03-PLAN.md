<objective>
Lock the generated MV3 manifest under an automated inspection test and resolve the content-script discovery defect as a recorded decision rather than a silent path fix.

Purpose: two defects already shipped behind a green build — the manifest carried an `options_ui` key that overrode the intent declared in `wxt.config.ts`, and the content script matched no WXT entrypoint glob and was silently excluded. Both are only visible in the built artifact, so both need a build-inspection test and an explicit decision. This plan is also where the least-privilege question the path fix raises — how wide the content script's host match should be in a phase that does not need it to run — is answered by the operator rather than by default.
Output: `tests/isolation/generated-manifest.test.ts` asserting the authorised manifest shape, a content-script entrypoint whose injection scope is decided and recorded, and an inventory entry that documents the §5.1 divergence.
</objective>

  <decision>
Which injection scope does the Phase 1 content script declare in the generated manifest?

The relocation in `01-02` renamed the file to `src/entrypoints/content/index.ts`, which matches WXT's `content/index.[jt]s?(x)` glob — so the content script is now discovered and its `matches` value becomes a host permission in the shipped manifest. Phase 1 runs no extraction: the content script's only action today is an advisory `CONTENT_SCRIPT_READY` message, and no Phase-1 acceptance criterion depends on it executing. PRODUCT_SPEC §16.4 sets least privilege as a hard rule and forbids adding a host permission silently, so the scope must be chosen rather than inherited.
  </decision>
  <context>
Evidence gathered this session: WXT 0.20.27's content-script glob table is `content.[jt]s?(x)`, `content/index.[jt]s?(x)`, `*.content.[jt]s?(x)`, `*.content/index.[jt]s?(x)` with `expandDirectories: false`; `content/core.content.ts` matched none of them and the generated manifest had no `content_scripts` key. PRODUCT_SPEC §5.1 lists the content entrypoint in Phase 1's Create list, but §18's Phase-1 DONE-when says nothing about it running. The existing `host_permissions` array is the ServiceNow host set; nothing else is currently authorised.
  </context>
  <options>
    - **Option A — keep the entrypoint, narrow `matches` to the already-authorised host set.** The content script is discovered and built, its injection scope equals the host permissions the manifest already declares, and no new host access is introduced. Phase 6 widens the scope when PageContentService lands. Lowest least-privilege cost; diverges from a literal `<all_urls>` reading of §5.1.
    - **Option B — keep `matches: ['<all_urls>']`.** Faithful to the prototype and to a literal reading of an extraction capability that will eventually run everywhere. Cost: the shipped Phase-1 manifest requests access to every site while no Phase-1 behaviour uses it — a real Web Store review and attack-surface cost for zero Phase-1 value.
    - **Option C — keep the entrypoint but exclude it from the build for Phase 1** (temporarily unmatched pattern, recorded in the inventory with a named owning plan and its removal condition). The structure stays canonical and the manifest stays narrow, at the cost of a temporary exclusion that must be removed on schedule.
  </options>
  <resume-signal>Select: A, B or C — or describe the injection scope the extension should declare in Phase 1.</resume-signal>
