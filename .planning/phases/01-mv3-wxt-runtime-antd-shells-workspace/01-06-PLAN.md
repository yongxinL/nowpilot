<objective>
Realign the runtime envelope to the canonical registry, validate message payloads, and close the missing sender guard on the background message path.

Purpose: success criterion 4 requires that background listeners register synchronously and that RuntimeEnvelope fixtures parse. Two gaps stand between the prototype and that criterion: the prototype's literal spellings diverge from Appendix E, and `MessageBus.init` registers its `chrome.runtime.onMessage` listener without checking `sender.id`, while `isEnvelope` validates only four key names and type membership. In an MV3 extension any context that can call `sendMessage` is a potential sender, so the guard and the payload schema are the phase's cross-context trust boundary.
Output: a canonical `MessageType` registry with schema-validated payloads, a sender-guarded message bus, a background router bound to the canonical literals, and an extended fixture suite proving both acceptance and rejection.
</objective>

<threat_model>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| any extension context → `chrome.runtime.onMessage` | Any context that can call `sendMessage` reaches this listener; `sender.id` is the only trustworthy identity field. |
| envelope payload → handler input | The payload is attacker-controlled data until a schema accepts it. |
| service-worker wake → listener registration | A listener registered after an `await` does not exist for the event that woke the worker. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-1-25 | Spoofing | `MessageBus.init` listener | high | mitigate | Reject any message whose `sender.id` differs from `chrome.runtime.id`, including absent sender and absent id; proven by dedicated cases asserting no handler ran. |
| T-1-26 | Tampering | `RuntimeEnvelope` payload | high | mitigate | Payloads are parsed by a strict Zod schema (`z.object(...).strict()`) with bounded string lengths; an unknown extra field or an oversized payload is a rejection, and dispatch validates before any handler sees the data. |
| T-1-27 | Repudiation | Declared `source` field trusted as identity | high | mitigate | Handlers never trust the envelope's declared `source`; the sender guard uses `sender.id` only. This is stated as a prohibition and asserted by the foreign-sender case. |
| T-1-28 | Denial of service | Missing listener after service-worker idle termination | medium | mitigate | `BackgroundRouter.register()` stays the first synchronous statement in `main()`, and the cold-start case asserts synchronous attachment; the guard is expressed as a grep assertion on line order relative to the first `await`. |
| T-1-29 | Elevation of privilege | Handlers for unimplemented capabilities | low | mitigate | Scaffold-local literals stay in a separate export with no handler registered, so no surface can claim a page-extraction or SPA-navigation capability the runtime does not implement. |
| T-1-SC | Tampering | npm/pip/cargo installs | high | mitigate | No install occurs in this plan; `zod@4.4.3` is already installed and was flagged `SUS` only on a `too-new` heuristic. Bumping it requires a blocking human checkpoint. |
</threat_model>
