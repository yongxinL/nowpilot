<objective>
Delete the prototype's plaintext provider credentials in place, idempotently and without relocating them.

Purpose: the prototype wrote provider keys into `chrome.storage.local` from five write sites, and any code holding the `storage` permission can read them. D-07 requires that they be removed now, that only recognised secret fields be removed, that authorised non-secret metadata survive, that the operation be idempotent and redacted, and that the value never be relocated, hashed, fingerprinted or retained — because Phase 2 owns KeyVault and Phase 1 must not create a holding place for the plaintext value. Because the deletion is irreversible and forces every existing user to re-enter credentials once secure storage exists, it is gated behind an explicit operator decision before the first write.
Output: a tested, throw-free sanitizer; an idempotent startup migration wired into the existing background registration contract; and one dismissible neutral notice.
</objective>

  <decision>
Confirm that Phase 1 deletes the legacy plaintext provider credentials in place, accepting that affected users must re-enter their credentials once Phase 2 ships secure credential storage.

This decision is rated **one-way**: the deletion destroys values that cannot be recovered from the client, and the repository cannot reconstruct them. The alternative — leaving the plaintext values in place until Phase 2 can migrate them — keeps the highest-severity finding open for the duration of the phase and conflicts with D-07's "strip secrets now", but it is the only option that avoids forcing credential re-entry.
  </decision>
  <context>
Evidence: provider keys are written to `chrome.storage.local` by five sites — the provider service (15 references), the onboarding modal (9), the extension store (4, including two top-level legacy key fields and four per-provider key fields), the Options page (4) and the shared types (1). Any extension context holding the `storage` permission can read them, and `CONCERNS.md` already records this as the top-severity finding. Phase 1 builds no secure storage, so the only choices are delete-in-place or carry the plaintext forward. There is no `.env` file and no environment-variable credential path in the repository, so the blast radius is bounded to stored configuration.
  </context>
  <options>
    - **Option A — delete in place now (D-07 as written).** Recognised secret fields are removed, authorised non-secret metadata is preserved, a redacted result is recorded, and the pinned neutral notice is shown once. Cost: users re-enter credentials after Phase 2 ships.
    - **Option B — leave the values and delete in Phase 2's migration.** No user re-entry cost, but the phase ships with a known plaintext-credential store and the highest-severity finding stays open through six or more weeks of development, including every manual Chrome session.
    - **Option C — delete now and additionally wipe the whole legacy provider configuration.** More thorough, but it destroys authorised non-secret metadata that D-07 explicitly requires be preserved, and it contradicts the "remove only the recognised secret fields" rule.
  </options>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `chrome.storage.local` legacy configuration → extension contexts | Any context holding the `storage` permission can read the stored plaintext credentials; the boundary closes only when the values are destroyed. |
| cleanup report → logs and UI | The report crosses into logging and, indirectly, into what the user is told; it must carry field names only and must not disclose presence. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-1-48 | Information disclosure | Plaintext provider credentials in `chrome.storage.local` | high | mitigate | The migration destroys them in place; the sentinel-absence suite asserts the value is absent from storage, session storage, per-origin storage, the persisted store, the report and the log buffer afterwards. |
| T-1-49 | Information disclosure | Cleanup report and logs | high | mitigate | Only field names are recorded; a source-level probe asserts the module contains no hashing, fingerprinting, masking or prefix-extraction path, so no derived value can be produced. |
| T-1-50 | Information disclosure | Relocation of the removed value | high | mitigate | The cleanup never writes the value anywhere else, never encrypts it, and a grep assertion fails if the sanitised configuration is broadcast or exported. |
| T-1-51 | Tampering | Partial or repeated cleanup | medium | mitigate | The operation is idempotent and version-stamped; the suite proves a second run removes nothing and returns deep-equal output. |
| T-1-52 | Repudiation | Disclosure of whether a credential existed | medium | mitigate | The notice copy is the pinned neutral sentence and the flag carries no found/not-found distinction to the UI; an over-wide report object is a prohibition and is asserted. |
| T-1-53 | Denial of service | Cleanup on every service-worker wake | low | mitigate | The cleanup short-circuits once the cleanup schema version is present, so repeated wakes are cheap and side-effect-free. |
| T-1-SC | Tampering | npm/pip/cargo installs | high | mitigate | No install occurs in this plan; no crypto dependency is introduced (Phase 1 adds no cryptography at all). |
</threat_model>
